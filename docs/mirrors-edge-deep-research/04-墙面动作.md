# 04 · 墙面动作

← [README](README.md) · 上一篇 [03-损速机制](03-损速机制.md)

墙面系统是镜之边缘辨识度最高的部分，也是参数最密集的部分。**这一章有本手册最重要的单条发现**（见 4.4）。

一个前置澄清：游戏里有**四个独立的墙面 Move 类**，社区术语经常把它们混为一谈：

| 类 | 触发情境 | 通俗叫法 |
|---|---|---|
| `TdMove_WallRun` | 侧向贴墙横跑 | wallrun |
| `TdMove_WallClimb` | 正面朝墙向上跑 | wallclimb / vertical run |
| `TdMove_WallKick` | 空中朝墙踢蹬 | wallkick |
| `TdMove_WallrunJump` | **从 wallrun 状态跳离** | wall boost ← 关键 |

---

## 4.1 Wallrun（贴墙横跑）

✅ **确证** — `TdMove_WallRun` CDO：

### 进入条件

| 参数 | 值 | 含义 |
|---|---|---|
| `WallRunningMinSpeed` | 200 uu/s | 低于 2 m/s 无法起跑 |
| `WallRunningVelocityStartLimit` | 300 | 起跑速度判定阈值 |
| `WallRunningMinWallHeight` | 192 uu (1.92 m) | 墙必须够高 |
| `WallRunningForwardMinStartAngle` | 0° | 正面入射角下限 |
| `WallRunningForwardMaxStartAngle` | **57°** | 正面入射角**上限** |
| `WallRunningStrafeStartAngle` | **60°** | 侧向入射角阈值 |
| `WallRunningForwardCheckDistance` | 50 uu | 前向检测距离 |
| `WallRunningStrafeCheckDistance` | 50 uu | 侧向检测距离 |
| `WallRunningDistanceForIntoWall` | 180 uu | 触发"扑向墙"的距离 |

**入射角是硬判定**：0–57° 走 forward 分支，60° 以上走 strafe 分支。57°–60° 之间这 3 度的缝隙很可能是有意的迟滞带（hysteresis），防止在临界角来回抖动。

### ✅ 实测：57° 是墙跑与爬墙的分水岭

✅ **逐帧实测**（2026-08，同一面墙，多角度反复进入，该段素材仅 0.7% 坏帧）：

```
进入 WallRun   的入射角： 4  4  6 15 36 45 48 49 51 55 55 56    ← 最大 55.6°
进入 WallClimb 的入射角：                      60 60 60 65 66    ← 最小 59.5°
```

**55.6° 与 59.5° 之间没有任何样本，`WallRunningForwardMaxStartAngle = 57` 正落在缝中。**
这是全手册中参数与实测吻合最干净的一处。角度以墙面为基准，因此 owner 观察到的
「>57° 且 <123°」与此处的「到墙面夹角 >57°」是同一件事（123° = 180° − 57°）。

📌 **超过 57° 不是"进不去"，而是"换一个动作"**——游戏把它判成垂直爬墙
（`WallClimb`）。这是个值得照抄的设计：**同一个输入按角度分流到两个动作，玩家不需要
学两套操作**，撞墙的角度自己决定了结果。

### ✅ 实测：只有 `Jump` 状态能进入墙跑，`Falling` 不行

15 次空中进入**全部来自 `Jump` 状态，无一来自 `Falling`**。两者的分界是
`TdMove_Falling.EnterToFallingZSpeed = -200`：下落快过 200 uu/s 即转入 `Falling`，
墙跑随即不可用。

⚠️ **但上限不是 `WallRunningVelocityStartLimit = 300`。** 本文档此前推断
「垂直速度须先降到 300 以下才能贴墙，故永远无法在抛物线前半段进入墙跑」——**实测推翻**：

```
实测进入墙跑时的垂直速度：-104 … +510 uu/s
```

+510 远高于 300，人还在上升段。**上升段完全可以贴墙**，`VelocityStartLimit = 300`
的真实语义仍然未明。

（另有 2 次 `WallClimb` 由 `Walking` 直接进入，入射角仅 9°——地面贴墙起攀是独立的
触发路径，不走上述角度判定。）


### 持续与衰减

| 参数 | 值 | 含义 |
|---|---|---|
| `WallRunningHorisontalFriction` | **0.05** | 贴墙期间摩擦力只有 5% |
| `WallRunningHorisontalAcceleration` | 820 uu/s² | 沿墙加速度 |
| `WallRunningHorisontalDeceleration` | 500 uu/s² | 沿墙减速度 |
| `WallRunningVelocityStopLimit` | −500 | 掉速到此值退出 |
| `WallRunningHorisontalInitialZHeight` | 170 uu | 进入时的初始抬升高度 |
| `WallRunningHorisontalAlignSpeed` | 700 | 对齐墙面的速度 |
| `WallRunningRotatePawnAlongWallTime` | 0.4 s | 身体转向贴合墙面的时长 |
| `MinimumVelocityIntoWall` / `Maximum` | 600 / 700 | 撞墙速度区间（触发镜头效果） |
| `RedoMoveTime` | 0.15 s | 冷却 |
| `TimeToDo90Turn` | 0.25 s | |

**没有"最长持续时间"参数**——但墙跑的时长其实是恒定的，原因不在水平方向。

### ✅ 实测：垂直方向被接管，时长与水平速度无关

📌 **本节此前的推断是错的**：曾把 `WallRunningVelocityStopLimit = -500` 读作"水平速度
衰减到 500 就退出"，并据此得出"跑得越快贴得越久，是纯粹由动量决定时长的设计"。
**那个值是垂直速度**（负号即下落），墙跑时长因此与你跑多快毫无关系。

✅ **逐帧实测**（2026-08，完整墙跑弧线抛物线拟合，rms 0.011–0.022 m）：

| 量 | 实测 | 占世界重力 |
|---|---|---|
| 上升段垂直加速度 | **~790 uu/s²** | 49% |
| 下降段垂直加速度 | **~505 uu/s²** | 32% |
| （对照）世界重力 | 1600 uu/s² | 100% |

两次独立弧线都显示**上升减速快于下落加速**（741/478 与 843/539），这个不对称是真实的，
效果是**快速到顶、缓慢下落**——贴上墙就"飘住"的手感来源。

于是时长闭环了：下落加速度约 500 uu/s²，从顶点掉到
`WallRunningVelocityStopLimit = -500` 恰好需要 **1.0 秒**。

```
贴墙        垂直重力降到 ~790（世界的一半）
+0.65 s     到达顶点，比起跳点高约 1.6 m
            重力进一步降到 ~505
+1.65 s     垂直速度触及 -500 uu/s，强制退出
```

水平方向由 `WallRunningHorisontalFriction = 0.05` 主管：实测**一秒只掉 4.9% 速度**
（保速 95.2%，理论 `exp(-0.05) = 95.1%`）。这才是墙跑作为保速载体的根据——
相比之下地面走路的有效摩擦是 8.0，**墙跑是它的 1/160**。

⚠️ `WallRunningHorisontalInitialZHeight = 170` 曾被本文档记作"进入时的初始抬升高度"。
实测**看不到任何瞬间抬升**：`SZD` 全程平滑，没有突变。玩家能升到比平地跳跃最高点
（1.24 m）更高的 1.6 m，完全由上面那个减半的重力解释，不需要位置补偿。
**该参数的真实含义仍未定。**

### 📐 墙该做多长

顶点固定在**贴墙后约 0.65 秒**，与速度无关，所以墙长应按进入速度换算：

| 墙长（满速 25.9 km/h 通过） | 用时 | 出口高度（相对起跳点） |
|---|---|---|
| 3 m | 0.44 s | +1.49 m |
| **4 m** | 0.59 s | **+1.64 m** ← 顶点 |
| **5 m** | 0.73 s | **+1.62 m** |
| 6 m | 0.88 s | +1.48 m |
| 8 m | 1.18 s | +0.85 m |
| 9.2 m | 1.40 s | +0.15 m ← 降回起跳高度 |

📌 **4–5 m 是最优解**，而且不只是"够用"：顶点附近高度曲线是平的（4 m 与 5 m 只差
0.02 m），**玩家早松手晚松手落点几乎一样**，对时机极其宽容。ME 关卡里墙跑普遍是这个
尺度。低速进入时按比例缩短（20 km/h 时顶点在 3.6 m），否则玩家会在下降段才到终点。

墙跑的物理极限约 11 m，但那需要**墙下悬空**——玩家要跌到起跳地面以下才能等到
`StopLimit` 触发。有地面的墙上，玩家 9.2 m 处就落地了。

### ⚠️ 两个把这一节带偏过的测量陷阱

1. **测量环境改变结论**。最初的墙跑素材是一面**下方悬空**的墙，玩家因此能跑满整条
   曲线；换成正常地形，玩家根本活不到 `StopLimit` 触发。物理极限与设计可用距离必须
   分开记录。
2. **状态标签缺失会让分段起点错位**。`WallRunningLeft/Right` 在上升段常常识别不出来，
   按状态标签分段会把弧线的起点定在**顶点**上，于是墙跑看起来"只有下降段、永远净
   下降"——由此得出的"可用距离 5.5–6.4 m""净下降 0.9 m"全是错的。
   **应当按弧线本身（`SZD` 离开零到回到零）分段，而不是按状态标签。**

### 镜头约束

✅ `MinLookConstraint = (-13000, -16384, -32768)`、`MaxLookConstraint = (13000, 16384, 32768)`

UE3 角度单位 65536 = 360°，换算：

- **Pitch（俯仰）限制 ±13000 = ±71.4°**
- **Yaw（左右）限制 ±16384 = ±90°**

贴墙期间玩家的视角被**硬性锁在 ±90° 的扇形内**，不能回头。配合 `bConstrainLook = True`、`bUseAbsoluteYawConstraint = True`。这是"贴墙时镜头自动看向前进方向"体感的来源——不是动画，是输入约束。

## 4.2 Wallclimb（垂直爬墙）

✅ **确证** — `TdMove_WallClimb` CDO：

| 参数 | 值 | 含义 |
|---|---|---|
| `WallClimbingVerticalStartAngle` | **33°** | 入射角阈值（源码里注释掉了旧值 `//55`） |
| `WallClimbingMaxDistance2D` | 120 uu | 水平检测距离 |
| `WallClimbingVelocityStartLimit` | 0 | **无最低速度要求** |
| `WallClimbingVerticalFriction` | 6.0 | 垂直摩擦（很高，快速衰减） |
| `WallClimbingGravity` | **800** | 世界重力（实测 1600）的**一半**——爬墙期间重力减半 |
| `AddOnSpeed2DHeight` / `MaxLimit` | 60 / 650 | 水平附加速度的高度与上限 |
| `AddOnSpeedZHeight` / `MaxLimit` | 130 / 320 | 垂直附加速度的高度与上限 |
| `MinWallHeight` | 180 uu | |
| `MinLegdeZNormal` | 0.707 | 可抓边缘的法线下限（= 45°），注意原文拼写错误 `Legde` |
| `FrictionModifier` | 0.3 | |
| `MinUpwardsVelocityToDoubleJump` | 100 | |
| `MaxIntoWallClimbVelocityToDoubleJump` | 100 | |

**关键对比**：wallclimb 的入射角阈值是 **33°**（要相当正对墙面），wallrun 是 **57°/60°**。这就是"对着墙跑就往上爬，斜着跑就横着跑"的判定分界。⚠️ 注释掉的 `//55` 说明 DICE 中途把这个阈值从 55° 收紧到 33°——大概是因为 55° 时玩家想 wallrun 却总是触发 wallclimb。**这条注释是难得的设计迭代痕迹。**

🔶 **推导爬升高度**（此处用 `WallClimbingGravity = 800`，不是世界重力）：`AddOnSpeedZMaxLimit = 320` uu/s，在重力 800 下能再爬升 320²/(2×800) = 64 uu；加上 `AddOnSpeedZHeight = 130`，总有效爬升在 **190–200 uu（约 2 m）** 量级，与 `MinWallHeight = 180` 自洽。

## 4.3 Wallkick（空中踢墙）

✅ **确证** — `TdMove_WallKick` CDO：

| 参数 | 值 | 公制 |
|---|---|---|
| `WallKickVelocity2D` | 300 uu/s | 3.0 m/s 水平 |
| `WallKickVelocityZ` | **580 uu/s** | 5.8 m/s 垂直 |
| `WallKickMaxDistance` | 60 uu | 离墙最大触发距离 |
| `WallKickCheckHeight` | 90 uu | 检测高度 |
| `WallKickExtentWidth` / `Height` | 20 / 10 | 检测盒尺寸 |
| `RedoMoveTime` | **1.0 s** | **同一动作 1 秒冷却** |
| `PawnPhysics` | `PHYS_Falling` | |

🔶 **推导轨迹**（假设 2D 分量是覆盖而非叠加）：垂直 580 → 滞空 2×580/800 = **1.45 s**，水平飞行 300 × 1.45 = **435 uu = 4.35 m**。

垂直分量 580 接近普通跳跃的 630——**踢墙几乎等于一次完整的额外跳跃**。这就是它作为爬升手段的价值。

⚠️ `RedoMoveTime = 1.0` 是本手册里最长的冷却之一，明确回答了你的问题：**不能对同一面墙连续快速踢**。1 秒的冷却意味着必须找到另一面墙，或者接受高度损失。

⚠️ 未确证：`WallKickVelocity2D = 300` 是**设置**水平速度还是**叠加**到现有速度。若是覆盖，踢墙就是净损速（因为跑速可达 720）；若是叠加，则是加速手段。📣 社区把 wallkick 主要当作**爬升/续航**手段而非提速手段，这倾向于"覆盖"或"设为最小值"。

## 4.4 ⭐ WallrunJump：DICE 把技巧梯度写进了参数名

这是本手册最重要的单条发现。

✅ **确证** — `TdMove_WallrunJump` CDO：

```
WallRunningPushAwaySpeedNoob         = 120      ← 字面意思：菜鸟
WallRunningPushAwaySpeedProAdd       = 400      ← 字面意思：高手加成
WallRunningPushForwardSpeedMin       = 0.1
WallRunningJumpOffZHeightForward     = 100
WallRunningJumpOffZHeightMaxAddTurned = 60
```

**DICE 直接在参数名里写了 `Noob` 和 `ProAdd`。** 从 wallrun 跳离墙面时获得的推离速度不是常数，而是一个区间：

```
最差执行:  120 uu/s
最好执行:  120 + 400 = 520 uu/s        ← 4.3 倍差距
```

同理垂直分量：基础 `100`，转身角度对时可再加 `60`（最高 160）。

### ✅ 实测：插值变量是**蹬墙时机**，不是朝向

✅ **逐帧实测**（2026-08，24 次蹬墙，两段控制变量录制）：

| 贴墙时长 | n | 中位速度增益 |
|---|---|---|
| **≤5 帧（贴上即蹬）** | 11 | **+5.12 km/h** |
| 6–29 帧 | 3 | +1.44 |
| 30+ 帧 | 10 | **+0.81** |

`corr(贴墙帧数, 增益) = -0.421`。单次最大 **+13.65 km/h = 379 uu/s**，与
`ProAdd = 400` 吻合。

📌 **`Noob` / `Pro` 的那个"技巧"，指的是反应速度**：贴上墙立刻蹬拿满 520 uu/s，
磨蹭到墙跑自然跑完只剩 120。这解释了社区为何把 wallboost 列为需要练习的技术。

⚠️ **朝向不是变量**（至少不是主要变量）：同一批数据里
`corr(墙跑期间视角扫过角度, 增益) = -0.193`，无相关。本节此前推断插值变量是
「离墙瞬间的视角朝向与墙面夹角」，**未获支持**——但也未被排除，因为两段素材的朝向
变化都不大（owner 在录制时刻意不碰鼠标）。要判定朝向是否叠加影响，需要固定时机、
只改朝向的第三组对照。

### ✅ 实测：连续蹬墙加速 glitch 偷的是"空中不限速"

owner 用滚轮当跳跃键，对着一堵长墙小角度反复瞬间蹬墙（**不是**两墙横跳；ME 落地前
最多允许两段墙跑）。九次循环的数据完全一致：

```
落地      速度被地面 ceiling 精确摁回 25.92 km/h (720 uu/s)
贴墙      +2.7
蹬墙      +7.2                    → 合计冲到 33-38 km/h
空中      AirSpeed 2400 几乎不限速，原样保持
落地      又被摁回 25.92
```

**九次落地速度全部精确回到 25.92,没有任何累积。** 这个 glitch 的收益不来自叠加，
而来自"**空中不受地面上限管辖**"这条规则——靠尽可能长时间待在空中，把平均速度拉到
地面上限之上。

📌 复刻时若把速度上限做成全局的（地面空中一视同仁），这类技巧连同它背后的表达空间
会一起消失。**上限只该管地面**，见 [02.3](02-速度系统.md#23-基础运动属性) 的
`AirSpeed = 2400`。

---

⚠️ 中间值由什么插值，参数名没说。📣 社区实测认为是**离墙瞬间的视角朝向与墙面的夹角**（见上方实测对此的检验）：

> 「贴墙跑时**尽量正面朝向所贴的墙**（但不要直接撞上去）再跳，会获得显著速度增益。」
> 「wallrun 时看向所贴的墙并起跳，速度可超过 20 mph（≈894 uu/s），高于常规跑速 16 mph 与跳跃 18 mph。」

社区管这个叫 **wall boost**，多年来只知其然（有帖子直言"for whatever reason gain speed"）。**逆向数据给出了答案：那不是 bug，是 DICE 显式设计的 120→520 技巧梯度。**

### 🎯 这条交叉验证的分量

| 社区观察 | 逆向数据 | 结论 |
|---|---|---|
| "wall boost 能超过常规速度上限" | 推离速度最高 520，且 `AirSpeed = 2400` 不限速 | ✅ 机制成立 |
| "增益大小取决于你朝向墙的角度" | 梯度确认，但实测显示插值变量是**时机**而非角度 | ⚠️ 部分修正 |
| "原因不明" | 参数名直接写着 Noob/Pro | ✅ **解答** |
| speedrun.com 把 wallboost 归为 glitchless 合法技术，还分出 Gap / Double / Pole 三种变体 | 是设计内机制，不是 bug | ✅ 社区判断正确 |

📣 另有社区结论：**wallrun 结束落地瞬间动量会大幅提升，常常直接拉满到最高冲刺速度**，某 wiki 称其为"游戏中最快的通用移动方式"。⚠️ 这与 4.4 的推离速度是否同一机制未确证。

### 对复刻的启示

**如果你的墙跳给固定冲量，你就丢掉了镜之边缘最核心的技巧梯度。** 这个 4.3 倍的区间是"新手能玩、高手有得练"的全部来源——它让同一个按键在不同执行质量下产生天差地别的结果，而且**不需要额外按键、不需要 QTE、不需要教学**。

## 4.5 墙面相关的其他跳跃

✅ **确证**：

| 类 | 参数 | 说明 |
|---|---|---|
| `TdMove_WallClimbDodgeJump` | `BaseJumpZ=700`、`JumpAddXY=150`、`DodgeJumpInertiaConservation=**1.0**` | 从爬墙状态侧跳，**100% 保留惯性** |
| `TdMove_WallrunDodgeJump` | `BaseJumpZ=300`、`JumpAddXY=600`、`InertiaConservation=**0.3**` | 从 wallrun 侧跳，只保留 30% 惯性，但水平推力 600 很大 |
| `TdMove_WallClimb180TurnJump` | `JumpOffZHeight=250`、`JumpPushAwaySpeed=400`、`JumpTimeWindow=**0.6**` | 爬墙后转身跳，**0.6 秒输入窗口** |
| `TdMove_DodgeJump` | `BaseJumpZ=300`、`JumpAddXY=600`、`InertiaConservation=0.3`、`StrafeThreshold=0.99` | 普通侧跳 |

**`DodgeJumpInertiaConservation` 是显式的惯性保留系数**——0.3 vs 1.0 的差别意味着"从哪个状态跳出去"决定了你能带走多少速度。这是一张需要玩家记忆的隐藏收益表，也是速通路线规划的基础。

### ✅ owner 实测：`TdMove_DodgeJump` 就是「闪避」，而且冲量是**绝对方向**

owner 在 ME 里实测，补齐了这一行 CDO 数值背后的玩法：

```
输入        A / D + 空格（侧移方向 + 跳）
效果        临时获得横向 ~25 km/h，并小跳一下
用途        躲攻击 —— 它首先是一个战斗动作，不是移动动作
```

🎯 **和 CDO 完全对得上，而且四个字段全部实装**：站定 dodge 实测恰好 **21.60 km/h
= 6.00 m/s = `JumpAddXY` = 600 uu/s**——这一条同时把单位尺度钉死为 **1 uu = 1 cm**。
`BaseJumpZ = 300` = 3.00 m/s，在 g = 16 m/s² 下最高点 `3²/(2×16) = 0.281 m`，
实测每次 dodge 的 `SZD` 峰值都是 **0.28 m**。`InertiaConservation = 0.3` 与
`StrafeThreshold = 0.99` 各自的实测见下。

### ⭐ dodge glitch：横向冲量锁的是**世界方向**，不是身体方向

owner 实测的速通技巧，而它同时是一条**实现约束**：

往左 dodge 的**瞬间**获得的横向力是绝对方向的。dodge 期间把镜头快速往左拉 90°、
同时按住 W，那 25 km/h 就变成了前进速度。斜向 dodge 同样成立。

**这不是一个可以"顺手修掉"的 bug，它决定了实现方式**：冲量必须在**进入动作的那一帧**
解算成世界向量并锁死，而不是每帧跟着当前朝向重算。要 1:1，就得照抄这个"错误"。

📣 与上面那条 side-jump boost 是**同一个动作的两种用法**：社区那条讲的是绕过加速曲线，
owner 这条讲的是绕过转向税（[03-损速机制](03-损速机制.md)）。两者都靠
`JumpAddXY = 600` 的一次性水平推力，都不需要任何额外输入。

### ✅ 实测推翻：`StrafeThreshold = 0.99` 量的是**轴**，不是输入向量

这一节此前把 0.99 读作「侧移输入必须几乎纯粹（点积 > 0.99）」。**那个读法是错的**，被下面这条实测直接否掉：

```
输入        W + A，然后空格
结果        触发一次左 dodge
```

W+A 若按归一化向量算，侧移分量只有 0.707，够不到 0.99。两件事要同时成立，只能是：**0.99 作用在未归一化的输入轴上**。UE3 的键盘每轴独立给 ±1，按住 A 时侧移轴就是满量程 1.0，同时按不按 W 都不改变它。

⚠️ **手柄上如何，未测。** 摇杆是模拟量，斜推 45° 时 X 轴真的只有 0.707，按上面的读法就不该触发 dodge——但一代首发于 PS3/360，手柄是一等公民，而 dodge 首先是躲攻击用的战斗动作，「必须把摇杆推到正侧才生效」不像是能过验收的设计。更可能是原作对摇杆做了方形化映射，或者 dodge 的触发根本没读这个字段。**这条存疑，需要一次手柄实测才能定。**

📌 **对移植的意义**：判据必须落在「轴推到多满」上，而不是玩家意图的方向向量。归一化会把键盘的满量程和摇杆的斜推压成同一个数，而原作对这两者的判定相反——这是设备差异，不是可以抹平的实现细节。

### ✅ 逐帧实测：dodge **保留 30% 水平动量**，`InertiaConservation = 0.3` 是真的

录屏逐帧读 Tweaks 调试 HUD，60 fps，11 次 dodge（`tools/hud_ocr_data/dodge2.csv`）。

**判据**：若水平动量真的被清零、身体只带 `JumpAddXY` 飞出去，那么**无论什么速度进入，
每次 dodge 的速度都该是同一个数**。实测不是：

| 入场速度 km/h | dodge 锁定速度 km/h |
|---|---|
| 0.00（真正站定） | **21.60** |
| 2.82 | 22.80 |
| 5.91 | 23.37 |
| 8.42 / 8.43（3 次） | 24.13 |
| 9.89（2 次） | 24.42 |
| 19.68 | 25.85 |
| 21.88 | 26.80 |
| 22.08 | 26.51 |

线性拟合 `V_dodge = 0.205 × V_入场 + 22.19`，**R² = 0.968**。

⚠️ **站定那一次恰好等于 6.00 m/s = `JumpAddXY` = 21.60 km/h，"动量清零"的读法在这一个
样本上完全正确。** 这正是它骗过人的地方——站定是唯一分辨不出两种读法的入场条件。

🎯 **三条独立佐证**：

1. **dodge 期间的前向分量不是 0。** 三次全速 dodge 实测前向 `+4.67 / +5.08 / +5.03 km/h`，
   侧向 `25.14 / 24.60 / 24.91`，方向偏离正前方 `79.5° / 78.3° / 78.6°`。清零读法预测前向恒为 0。
2. **按 `|0.3·v_入场 + 6.0·ŷ|` 反解**，三次分别要求入场速度偏前 42.3° / 40.8° / 47.2°，
   由此预测的前向分量 4.90 / 4.47 / 4.46 km/h，与上面实测的 4.67 / 5.08 / 5.03 相符。
3. **落地那一帧 HUD 恰好读 25.92 km/h**，即地面跑速上限。空中确实带着超过上限的速度，
   落地被 clamp——这也正是 side-jump boost 有价值的原因。

📌 **所以 dodge 出来比进去时更快**：25.58 km/h 巡航进入，锁定 26.51 km/h。这不是读错，
这就是这个动作。

### ✅ 逐帧实测：dodge **不扣速度能量**

此前记为「dodge 把速度能量清到 base velocity（14.4 km/h）」。**这条也是错的。**

⚠️ 全速 dodge 之后速度确实会掉到 **16.04 / 16.20 / 16.12 km/h** 再回升——但那是**速度矢量
被落地时按住的 W 掰回来**的损失，不是天花板被压低。两者的区别用 dodge glitch 直接分开：

| glitch 次数 | 落地 V | 落地后 0.5 s | 落地后 1.0 s |
|---|---|---|---|
| 转 −90.1°（最快） | 24.90 | 25.06 | **25.80** |
| 转 +77.1° | 24.13 | 24.58 | 24.94 |
| 转 −85.7° | 22.30 | 23.16 | 23.90 |
| 转 +53.6°（最慢） | 22.80 | 23.12 | 23.87 |

四次**落地即开始爬升，没有一次被拖向 14.4**。若天花板真被压到 base velocity，这四条曲线
都该被从上面压下来。**而且那样会直接毁掉 side-jump boost**——这个动作在非战斗场景的全部价值。

🎯 **那三次掉到 16.1 的，损速全部发生在两端，`DodgeJump` 状态自己一分不损**：

| 阶段 | 时长 | V |
|---|---|---|
| 按下侧键 → dodge 触发 | ~100 ms | 25.55 → 22.08（普通 `Walking` 转向税） |
| `DodgeJump` 锁速 | 367–383 ms | **恒定不变**，一个小数位都不动 |
| 落地那一帧 | 1 帧 | 25.92（地面上限 clamp） |
| 矢量被 W 掰回来 | ~100 ms | 25.92 → 16.04 |
| 重新加速 | ~2 s | 16.04 → 25.58 |

📌 **代价换算**：从触发到速度恢复约 2.5 s，前进只走了 12.31 m，直跑本该 18.00 m——
**净亏 5.7 m，约等于白跑 0.8 秒**。

🎯 **「跑动中误按 dodge」确实很伤**，但伤在转向税收了两次（进和出），不在动作本身。

⚠️ **转头不完美不会丢速度，只会推迟回到上限。** 上表最慢那次落地时只转完 60%，速度照样
保住 94%，只是花了 2300 ms 才爬回 25 km/h，而转得最快的一次只用 **167 ms**。

📌 **状态期间世界坐标的移动方向完全不变**（实测转头 90° 全程 heading 保持 0°–2.7°）。
转镜头只是把这个既有速度矢量重新贴上「前方」的标签，落地时 W 与它夹角越小，
`Walking` 要掰的角度越小，损速越少。这和上面「直跑 dodge 损 37%」是**同一个机制的两端**。

📣 社区的 **side-jump boost / sidestep boost**（侧走起跳后空中转身即达最高速）正是利用这个动作——`JumpAddXY = 600` 的水平推力配合空中转向，绕过了 [02](02-速度系统.md) 那条 7 秒的加速曲线。社区称其为一代绕过加速曲线的主要手段，且属 glitchless 合法。

## 4.6 Shimmy（挂边横爬）与九十度转角

### ✅ 实测：按住 A/D 时，横爬**赢过**镜头——游戏会把头扭回来

owner 在原作实测。这不是"转头太多就不给爬"，而是**反过来**：按住左右键时，游戏优先保证爬行操作，主动把视角带回可爬的范围。

| 按住 A/D 时视角偏离墙面 | 原作行为 |
|---|---|
| ≤ 45° | 正常横爬 |
| 45°–90° | **照爬**，同时把视角**拉回** ±45°，按住期间钳制临时收成 ±45° |
| > 90° | **不帮忙**——这被读作**反身跳**的意图，抢走它比拒绝横爬更糟 |

📌 **这条判据逐帧成立，不需要在按键按下那一刻锁存**，而且不锁存反而更对：

- 按住期间钳制就是 ±45°，**视角根本甩不回 90° 以外**，除非松手——所以"爬到一半被鼠标甩断"不会发生
- 反过来，在 120° 时按住 A/D 不放、然后自己把头转回 90° 以内，横爬**自然就开始了**（owner 实测确认）。这一条不用专门写代码，它是同一条规则的另一面

⚠️ **"拉回视角"不需要单独的转向逻辑。** 本项目实现时发现：`CameraRig` 对"扇形收窄到视角之外"的处理本来就是**让扇形边缘平滑地追上视角**，而不是把视角切到边界（墙跑重新对准墙面走的是同一条路径）。所以**把扇形收成 ±45° 就等价于"以镜头常规平滑速度把头带回来"**。

📌 松开 A/D 后视角**停在被带回的位置**，不回弹到原来的朝向——被移动两次会读作镜头被抢了两次。


`TdMove_Grab` 的 CDO 里有横爬的**全部证据，唯独没有速度**：

```
CurrentShimmyMove                        NoShimmy      ← 枚举，说明有左/右两种
ShimmyAroundCornerMinLookContraint       (3200, -32768, 0)     俯仰 17.6°~87.9°
ShimmyAroundCornerMaxLookContraint       (16000, 32768, 0)
ShimmyAroundCornerFreeMinLookContraint   (11000, -32768, 0)    俯仰 60.4°~87.9°
ShimmyAroundCornerFreeMaxLookContraint   (16000, 32768, 0)
DisableShimmyTime                        0.6
```

没有任何速度字段——原版多半是让动画驱动的。

### ✅ owner 实测

```
横爬速度   2.15 km/h = 0.597 m/s
节奏      平均 1 s 爬一下，然后约 0.3 s 换手
外 90° 转角  约 1 s 转过去，期间锁镜头
```

⚠️ **速度是平均值，不是匀速**。1 s 移动 + 0.3 s 换手的循环里，真正在动的那 1 s
接近 **0.78 m/s**，然后停死。复刻时先用匀速 0.597 也对得上距离，但少了那个顿挫。

📌 **一个假读数值得记下来**：第一次读 HUD 得到的是 **18 km/h**，那会把横爬放到
Run（400 uu/s）和 Sprint（630）之间——手递手比冲刺还快，不可能。原因是
`TdMove_Grab` 的 `PawnPhysics = PHYS_None`：**挂着的时候物理不更新速度**，HUD 显示的
是抓上去之前带进来的那个数。挂着不动再读一次就露馅了。

### 🎯 「锁镜头」和 `Free` 那组钳制对得上

owner 对外角的判断是「可能是怕穿帮」。CDO 支持这个读法：

| | 俯仰范围 | 相对常规 |
| --- | --- | --- |
| 常规挂边 `MinLookConstraint` | −17.6°~+87.9° | 基准 |
| `ShimmyAroundCorner*` | +17.6°~+87.9° | 掐掉了往上看 |
| `ShimmyAroundCornerFree*` | **+60.4°~+87.9°** | 只剩一条 27° 的窄缝 |

`Free` 那组把视线**压进一条几乎垂直的窄带**——而且 60.4° 已经超出了游戏常规的
±54.9°（`MinLookConstraint = ±10000`）视角范围。也就是说绕外角时镜头被推到一个
平时根本到不了的角度上，正对着自己的手或脚。**这不是限制玩家乱看，这是强制他
只能看一个不会穿帮的方向。**

⚠️ 「`Free` = 外角」仍是**推断**。命名上 free 指身体悬空（外角绕过去时背后是空的），
钳制更紧也符合外角更容易看穿几何——但 CDO 里没有一句话直说哪组对应哪种角。
owner 实测的「外角锁镜头」和这组更紧的钳制**方向一致**，这是目前最强的旁证，不是证明。

📌 `DisableShimmyTime = 0.6` 大概率是转角**之后**的横爬禁用窗口——防止在角上来回抽搐。
配合实测的 1 s 转角时长，一次完整的绕角是 **1.0 + 0.6 = 1.6 s** 的不可打断段落。
