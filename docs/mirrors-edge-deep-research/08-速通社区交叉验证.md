# 08 · 速通社区交叉验证

← [README](README.md) · 上一篇 [07-Catalyst对照](07-Catalyst对照.md)

本章把 [01](01-方法论与可信度分级.md) 里的两条数据管线对起来：**逆向数据说"参数是多少"，社区说"玩起来是什么样"**。两边吻合的地方可信度最高；两边冲突的地方最值得研究。

在线调研共产出 **99 条去重 claim**（完整原文见 [附录 A3](appendix/A3-在线调研原始claim.md)，来源清单见 [附录 A4](appendix/A4-来源URL清单.md)）。

## 8.1 ✅ 精确吻合（可信度最高）

| # | 社区说法 | 逆向数据 | 判定 |
|---|---|---|---|
| 1 | 「最高跑速 16 mph / 26 km/h」 | `GroundSpeed = 720 uu/s` → 7.2 m/s = **25.92 km/h = 16.10 mph** | ✅ 吻合，且**反向确认了 1 uu = 1 cm** |
| 2 | 「从静止到全速冲刺要 7–10 秒」 | `SpeedCurve_LightWeapon` X 轴终点 = **7.0 s** | ✅ 吻合 |
| 3 | 「wall boost 增益取决于你朝墙的角度，但原因不明」 | `WallRunningPushAwaySpeedNoob=120` / `ProAdd=400` | ✅ **逆向数据解答了社区多年的疑问** |
| 4 | 「slide 是游戏里最慢的动作，没有速度收益」 | `TdMove_Slide` 无任何加速项，只有 `FrictionModifier=0.1` 和 2 秒硬时限 | ✅ 吻合 |
| 5 | 「wallboost 是 glitchless 合法技术，不是 bug」 | `Noob`/`ProAdd` 是显式设计参数 | ✅ 社区判断正确 |
| 6 | 「跳跃时速度提升到 18 mph（比跑速高 12.5%）」 | `AirSpeed = 2400` 不构成约束，地面 720 的上限在空中不生效 | ✅ 机制成立 |

第 1 条尤其重要：它是一条**独立于逆向管线**的实测，却与逆向值吻合到小数点后。这基本排除了我的解析出错的可能，也解决了 UE3 单位比例的歧义（官方文档明确说 UT 系列用 1 uu = 2 cm、"多数被授权方"用 1 uu = 1 cm，本身给不出答案）。

## 8.2 🔍 社区现象 → 逆向数据给出机制解释

| 社区技巧 | 逆向数据中的对应机制 |
|---|---|
| **Side-jump / Sidestep boost**（侧走起跳 + 空中转身 = 瞬间满速，绕过 7 秒曲线） | `TdMove_DodgeJump`：`JumpAddXY = 600`、`StrafeThreshold = 0.99`、`DodgeJumpInertiaConservation = 0.3` |
| **Wall boost**（贴墙跑时朝向墙面起跳获得大幅增速） | `TdMove_WallrunJump`：`PushAwaySpeedNoob=120` → `+ProAdd=400` |
| **Ventkick / Kickglitch / Drop-Roll / Fall-Break Kick**（重置坠落高度） | 落地惩罚基于**累计下落高度计数器**，任何触地事件都能重置；见 [03.5](03-损速机制.md#35-绕过损速的社区技巧机制原理) |
| **Kick Momentum Cancel**（踢击清动量） | 踢击类 Move 未声明惯性保留，`TdMove_MeleeSlide.FrictionModifier=0.1` 等 |
| **3-step Rule**（落地后要直行 3 步再转向） | `SpeedTurnDecelerationFactor = 10` 与落地损速叠加，见 [03.2](03-损速机制.md#32-转向损速) |
| **Coil boost**（coil + 顺滑落地 = 最高速） | ⚠️ coil 只有 `TotalHeightBoost = 60`，**没有速度加成**——推测是间接规避落地损速，见 [05.2](05-动作库总览.md#52-coil空中收腿) |
| **不同 vault 有速度差** | `VaultTypes` 的 6 段高度表，中段有 `SpeedAddition = 80`，高段被钳到 200–400，见 [05.7](05-动作库总览.md#57-vault翻越) |

## 8.3 ❓ 冲突与未决

| 问题 | 状态 |
|---|---|
| `LandingSpeedReduction = 65` 的单位（损失 65%？保留 65%？减 65 uu/s？） | ❓ **本手册最重要的未决问题**。社区只有"几乎归零"的定性描述 |
| Kickglitch 的隐形平台持续几帧 | ❓ 社区有 **1–2 帧**与 **3 帧**两种说法，来源冲突 |

## 8.4 ⚠️ 关于验证流程本身的两个教训

在线调研跑了一套「3 票对抗性验证」流程（每条 claim 由 3 个独立 agent 尝试证伪，2/3 反对即淘汰）。本地一手数据到手后，可以反过来给这套流程打分——结果值得记录：

**教训一：验证流程正确推翻了一条错误结论。**

有一条 claim 主张：ME 的移动核心参数（GroundSpeed / AirSpeed / AccelRate / JumpZ / 重力）**没有以 .ini 形式暴露**，必须反编译才能拿到。这条被 3 票推翻。**本地安装目录直接证明它是错的**——`TdGame\Config\DefaultPawnMovement.ini` 与 `DefaultGame.ini` 都是明文，重力、`BaseJumpZ`、全部墙面参数都躺在里面。

该 claim 的来源只看了 `Documents\EA Games\...` 下的**用户侧**配置目录，漏掉了**安装目录**下的 `Default*.ini`。这是一个典型的"来源本身不完整"而非"推理错误"的失败。

**教训二：验证流程也误杀了一条正确结论。**

另一条 claim 主张 ME 的包版本是 **3716 / 536 / 043**，同样被 3 票推翻。而我自己解析包头得到的是：

```
EngineVersion = 3716    FileVersion = 536    LicenseeVersion = 43
```

**完全一致。** 验证 agent 大概是无法确认"UELib 的 README 里是否真有这一行表格"，就把整条连同其中正确的事实一起否掉了。

**结论**：对抗性验证能过滤幻觉，但**它验证的是"来源是否支持该表述"，不是"该表述是否为真"**。当一手数据可得时，一手数据永远优先于任何投票机制。这也是为什么这份手册把本地逆向放在 [01](01-方法论与可信度分级.md) 的来源 A/B、把在线调研放在来源 C。

## 8.5 开发者一手资料（设计意图）

这部分逆向数据给不了，只能靠访谈。全部 📣 primary 但**零数值**：

- **动量是核心支柱**：制作人 Nick Channon 称 momentum「就像驱动你通关的燃料，这是最重要的部分」。
- **移动是唯一核心**：「我们想做一个完全关于移动的游戏」。枪械是**开发中途被移除**的，此后团队再无射击玩法作退路，被迫把移动做到能独立支撑整个游戏。
- **第一人称是手段不是类型**：「一旦变成第三人称，你就是在**看** Faith，而我们希望你与她**连接**」。
- **FOV 开到最大**：DICE 把 FOV 开到「画面开始弯曲之前」的最大值，理由是窄 FOV（举例 40°）造成方位感丧失与晕动症。📣 社区确认默认值为 **90°**。
- **head bob 被移除**：DICE 在开发中**移除了早期版本的 head bobbing**，重新表述目标为「从你的**眼睛**看世界，而不是从你的**头**」。⚠️ **这直接反驳了"镜之边缘靠强烈 head bob 制造速度感"的常见假设**——详见 [10](10-镜之边缘-like判定标准.md)。
- **专用第一人称骨骼**：Faith 有脊椎、颈、肩的第一人称 rig，摄像机由身体驱动。有一套由肩部驱动头部的方案因为**15 秒内就让人晕**而被推翻。准则是「大脑预期什么发生，就必须发生」。
- **Roll 镜头用芭蕾 spotting 原理**：翻滚时头部甩转后**回到与触发前相同的注视方向**，专门为防晕设计。→ roll 的镜头**不是**自由跟随身体旋转。
- **准心点是防晕装置**：屏幕中央白点「部分绑定摄像机 + 由远处焦点控制」，灵感同样来自芭蕾舞者的 spotting。
- **看得见的腿被砍了**：DICE 做了一整套 Faith 腿部与环境交互的系统，**因工期不足在发售版关闭**。
- ❓ **GDC 2009 有一场 DICE 一手演讲**《Creating First Person Movement for MIRROR'S EDGE》（讲者 Jonas Åberg、Tobias Dahl），但 **GDC Vault 付费墙**，本次未能获取正文。这是已知的最大资料缺口。（顺带更正：常被引用的 Tom Farrer 并非此场讲者。）
