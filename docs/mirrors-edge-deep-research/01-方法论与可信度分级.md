# 01 · 方法论与可信度分级

## 数据来源

本手册的数值来自四条独立管线，互相交叉验证。

### 来源 A：游戏原始配置文件（明文）

Steam 正版《Mirror's Edge》(2008) 安装目录：

```
<Steam>\steamapps\common\mirrors edge\TdGame\Config\
    DefaultPawnMovement.ini    ← 全部移动动作的调参
    DefaultGame.ini            ← Pawn 基础属性、重力
    DefaultAnimation.ini / DefaultCamera.ini / DefaultInput.ini
```

游戏内部代号是 **Takedown**，所以类前缀全是 `Td`。这些 `.ini` 是明文，直接可读，是可信度最高的一手数据。

### 来源 B：编译后 UnrealScript 包的反序列化（自研工具）

`TdGame\CookedPC\TdGame.u`（29 MB）包含全部游戏逻辑。它是 **LZO 压缩**的 UE3 包（FileVersion 536 / LicenseeVersion 43），需要先解压再解析：

1. `tools/ue3_decompress.py` — 解析包头的 compressed-chunk 表，逐块 LZO 解压 → 58.9 MB 平坦文件
2. `tools/ue3parse.py` — 解析 name table / import table / export table（20592 names、2246 imports、52410 exports、916 classes）
3. `tools/dump_cdo.py` — 解析每个 `Default__<Class>` 对象的 tagged property 列表，得到类默认属性
4. `tools/dump_struct.py` — 递归解析嵌套 struct 与 array（速度曲线就藏在这里）

`TdGame.u` 与 `Engine.u` 合计 **2031 个 CDO 全部解析成功，0 失败**。

> **踩过的坑**（复现时注意）：
> - export 表在 FileVersion < 543 时含 `ComponentMap` 字段，漏掉会导致偏移全错
> - 本版本的 `ByteProperty` tag **不含** enum 名字段，8 字节直接是值的 FName
> - `BoolProperty` 的值是 **4 字节 int**，不是 1 字节

**这不是破解**：读取的是自己合法购买的游戏的数据文件，不涉及绕过 DRM，也不分发游戏资源。仓库里只有提取出的数值和自研脚本。

### 来源 C：速通社区与在线调研

见 [08-速通社区交叉验证](08-速通社区交叉验证.md)。

### 来源 D：游戏内 HUD 的逐帧实测（自研工具）

Mirror's Edge Tweaks mod 自带调试 HUD，显示坐标、状态机状态、速度，以及三个**峰值记录器**
（`ZT` 最高点 / `VT` 最高速 / `SZ`+`SZD` 起跳点与相对高度）。
`tools/hud_ocr.py` 把录像逐帧解析成 CSV，实现定量测量。

**这条管线是后加的，但它推翻了前三条得出的若干结论**——最典型的是重力和起跳初速
（见 [02.4](02-速度系统.md#24-重力与跳跃)）。原因很简单：来源 A 给的是**配置值**，
而配置值不等于**生效值**。原生 C++ 可以在读取后再做任何处理，`.ini` 里看不见。

用法与踩坑见 [tools/README-hud_ocr.md](tools/README-hud_ocr.md)。

> 📌 **为什么必须录像**：游戏没有任何日志或数据导出——`TdGame` 目录下没有 `Logs/`，
> 且 `TdEngine.ini` 用 `Suppress=Dev*` 关掉了开发期日志分类。控制台可以恢复
> （把 `ConsoleClassName` 改回 `Engine.Console`），但没有能打印状态的命令。

## 可信度分级

全手册统一使用以下标记：

| 标记 | 含义 |
|---|---|
| ✅ **确证** | 直接从 `.ini`/CDO 二进制读出的原始数值，或由来源 D 逐帧实测直接测得，无解释成分 |
| 🔶 **推导** | 由确证数值经物理公式计算得出（如跳跃高度 = v²/2g），计算过程已给出 |
| ⚠️ **推断** | 参数名含义或语义由命名和上下文推测，**未经字节码验证** |
| 📣 **社区** | 来自速通社区实测或共识，非一手数据 |
| ❓ **未知** | 找不到、或来源互相矛盾 |

### 代码里的写法

这套刻度在**代码注释里用 ASCII 标签**书写，与上表一一对应：

| 手册 | 代码注释 |
|---|---|
| ✅ 确证 | `[ME:CONFIRMED]` |
| 🔶 推导 | `[ME:DERIVED]` |
| ⚠️ 推断 | `[ME:INFERRED]` |
| 📣 社区 | `[ME:COMMUNITY]` |
| ❓ 未知 | `[ME:UNKNOWN]` |

出处可以写进标签内部：`[ME:CONFIRMED 02 §2.4]`。

不用 emoji 的理由是实测的：本手册的五档落到代码里长成了十三种符号，🔶 只用了 1 次、
📣 一次没用，而 ✅ 有约四成标的是设计决定——不属于这套刻度覆盖的东西。字形不携带定义，
外部世界赋予 ✅ 的「通过 / 搞定」会压过本手册的定义，且它看起来像装饰，会被后来的人
当噪音删掉。

本手册自身继续用 emoji：这里的标记出现在带「标记 / 含义」表头的表格里，局部语境已经
消歧，不存在同样的漂移。

### 本研究的已知边界

**没有做字节码反编译。** `TdGame.u` 里的 UnrealScript 函数体（即真正的**公式**）没有解出来——只解了数据，没解代码。因此：

- 所有**参数值**是确证的；
- 所有**参数如何被使用**（乘上去？减掉？作为上限？）在没有社区实测佐证时只能标 ⚠️。

典型例子：`LandingSpeedReduction = 65` 这个值 100% 确证，但它是"损失 65%"还是"保留 65%"还是"减去 65 uu/s"，二进制数据本身回答不了。这类问题正是交叉验证要解决的，见 [03-损速机制](03-损速机制.md)。

#### ⚠️ 关于「用 UE Explorer 就能补齐公式」——此路不通

本文档此前建议：用 **UE Explorer**（EliotVU 的 UE3 反编译器）打开 `TdGame.u` 反编译出
UnrealScript 即可拿到公式。**经查证，对本研究最关心的几个公式，这条路走不通。**

`SpeedCurve_LightWeapon`、`SpeedEnergyDecelerationTime/Exponent`、
`SpeedTurnDecelerationFactor` 这些属性在 `TdGame.u` 里**零脚本引用**，也不存在名字相关的
函数——它们是被**可执行文件里的原生 C++** 直接消费的。UnrealScript 反编译器只能还原
`.u` 里的脚本字节码，拿不到原生代码。同类情况还有：**实际重力是配置值的 2 倍，
而所有 `.ini` 里都没有这个倍率**。

📌 **因此「速度能量如何累积」「转向减速如何计算」这类问题，在当前手段下不可能从数据
文件求解**，只能靠来源 D 的逐帧实测去拟合外部行为。这是本研究的硬边界，不是待办事项。
