## 5.1 Slide（滑铲）

```
SlideAbortSpeed   = 250        速度低于此值退出滑铲
SlideAbortTime    = 2.0 s      最长持续 2 秒
FrictionModifier  = 0.1        摩擦力 10%
MaxFloorInclineZ  = 0.5        可滑地面的最大坡度（60°）
MinLookConstraint = (-10000, -10000, 0)   镜头限制 ±55°
```

**滑铲没有任何速度增益参数。** 它只是把摩擦力乘以 0.1，然后靠两个条件之一结束。

### ✅ 实测：结束滑铲的是速度，不是时间

✅ **逐帧实测**（2026-08，5 段滑铲）：


| 入速 km/h | 时长   | 出速 km/h |
| ----------- | -------- | ----------- |
| 25.78     | 1.33 s | 8.92      |
| 22.18     | 1.15 s | 8.95      |
| 25.74     | 1.32 s | 8.99      |
| 21.78     | 1.13 s | 8.90      |
| 25.18     | 1.32 s | 8.90      |

**5 段全部由速度条件结束**，出速紧贴 `SlideAbortSpeed = 250 uu/s = 9.00 km/h`；
最长的一段只有 1.33 s，**`SlideAbortTime = 2.0` 从未被触发**。

📌 平地上速度总是先到底，2 秒的时限轮不到——它只在坡度让速度维持住时才有意义
（`DownwardSlideFrictionScale` 让下坡滑铲衰减更慢）。

⚠️ **`FrictionModifier = 0.1` 不是「几乎无摩擦」。** 它是乘在引擎默认
`GroundFriction = 8.0` 上的系数，有效摩擦 0.8，时间常数 1.25 秒——上表反解出的衰减率
是 0.79/s，与之吻合。详见 [03.3](03-损速机制.md#33-摩擦力模型)。
即使从满速入场，滑铲也只能滑 1.3 秒就掉到 9 km/h。

🎯 **交叉验证**：这与 📣 社区的强烈共识完全一致——

> 「我知道它看起来和感觉都很酷，但它是游戏里最慢的动作。」

社区认为 slide 唯一有价值的场景是 slide-kick（踢门）和矮通风管道。**逆向数据确认了这一点**：没有加速项，只有摩擦衰减和硬性时限。

⚠️ 注意 [03.3](03-损速机制.md#33-摩擦力模型) 的 `UpwardSlideFrictionScale = 5.0` / `DownwardSlideFrictionScale = 1.8`：滑铲的坡度敏感度极高，**下坡滑铲是全游戏少数的净加速情境**。

## 5.2 Coil（空中收腿）

```
CoilMinTriggerSpeed = 100          最低触发速度
CoilTime            = 0.5 s        动作时长
HeightBoostDuration = 0.25 s       抬升持续
TotalHeightBoost    = 60 uu        抬升总量（0.6 m）
MinLookConstraint   = (-5000, ...)  俯仰限制 −27.5°
MaxLookConstraint   = (30000, ...)  俯仰限制 +165°  ← 允许极端抬头
```

Coil 给 **+60 uu（0.6 m）的额外净空**，代价是 0.5 秒的动作锁定。

📣 **游戏内实测确认 `CoilMinTriggerSpeed = 100` 的语义**（Steam 正版，2026-08）：原地垂直起跳后在空中按下蹲键**没有任何动作**；带水平速度起跳后按下蹲键则触发 coil。100 uu/s = **1.0 m/s** 就是这个门槛。此前标 ⚠️，现可标 ✅。

### ⭐ 一个按键、四种结果

同一次实测顺带覆盖了 `GBA_Crouch` 的全部分支，是 [06.4](06-Move状态机架构.md#64-输入层只有两个上下文动作键)「复杂度在上下文解析里」的直接证据：


| 角色状态 | 条件                                          | 结果       |
| ---------- | ----------------------------------------------- | ------------ |
| 空中     | 水平速度 ≥ 1.0 m/s（`CoilMinTriggerSpeed`）  | **Coil**   |
| 空中     | 水平速度 < 1.0 m/s                            | **无动作** |
| 落地瞬间 | 坠落高度 ≥ 2.0 m（`SkillRollLandingHeight`） | **Roll**   |
| 落地瞬间 | 坠落高度 < 2.0 m 且有水平速度                 | **Slide**  |
| 地面     | 无水平速度                                    | **Crouch** |

**一个键，五个出口**，判据只有三个：在空中还是落地瞬间、水平速度、累计坠落高度。没有组合键、没有长按短按、没有方向修饰。

⚠️ 📣 **一处存疑**：社区实测称 **coil boost 是全游戏最高速度手段**（"约 30"，对比普通冲刺"约 26"，进入门槛速度"约 20"）。但 CDO 里 coil **只有高度加成，没有速度加成**。

我的推断：所谓 coil boost 的增速可能并非来自 coil 本身，而是来自「coil 抬高了落点 → 减少了累计下落高度 → 规避了 [03.1](03-损速机制.md#31-落地损速) 的落地损速」的**间接效应**。也就是说，它不是加速，是**免于减速**。⚠️ 未验证，但与社区描述的"coil-jump + 顺滑落地"这一执行要点吻合。

📣 社区另有结论：攀爬高处边缘时 coil 比 speedvault 更快。

### ✅ 胶囊怎么缩：以**中心**为准，不是以头也不是以脚（owner 实机探明）

owner 用 **ME Tweaks 作弊菜单的碰撞箱可视化**直接读出来的，不是推断：

> 「胶囊缩放不是以头为准！是以中心为准！也就是说同时会增加头顶的空间」

于是 coil 和 crouch 的关系变得非常干净——**同一个胶囊，同一个目标高度，两个锚点**：

| 动作 | 锚点 | 结果 |
| --- | --- | --- |
| Crouch | 底部 | 头降下来，脚不动 |
| Coil | **中心** | 脚抬起来，头顶**同时**多出同样的空间 |

📌 头顶也多出空间这一半，是「钻过矮缝」这类用法的来源；脚抬起来那一半才是过沟和避障。
两件事，一次缩放。

⚠️ **与 CDO 的一处对不上，记录而不弥合。** 按本项目的胶囊（站立 1.8 m、蹲下 0.9 m）中心
缩放，脚只抬 (1.8−0.9)/2 = **0.45 m**，而 `TotalHeightBoost` 说 **0.6 m**。两个数不可能
被同一个值同时满足。实测量的是「coil 高度 == crouch 高度」这个**关系**，CDO 量的是原作
自己那具 1.76 m 身体的**绝对值**，比例本来就没有义务活过移植。本项目取了关系，
`CoilConfig.capsule_height` 是个旋钮。

### ✅ 后摇：腿一直收着到 `CoilTime` 结束

owner：「coil 会有一个最大持续时间以及后摇，在此期间无法触发 StepUp 或 Grab」。

这句话把两个一直显得冗余的 CDO 时长解释通了——它们不是「0.25 秒收 + 0.25 秒别的」：

```
0    → 0.25 s   HeightBoostDuration   收腿，缩到位（这是渐变时长）
0.25 → 0.5  s   CoilTime 的剩余       保持收着（这就是后摇）
整个 0.5 s                            三种探测全关
```

### ✅ 只能从 `Jump` 进入

owner 实测：「实测只能 Jump 进入」，与 [11.3](11-状态机全图.md#113-空中主链) 的状态图一致
（图上只有 `Jump --> Coil` 一条边）。

🎯 **这条窄限制顺带解决了一个输入冲突。** coil 和落地翻滚读的是同一次蹲键按下，而
`EnterToFallingZSpeed` 只有 −2 m/s——一个准备落地翻滚的玩家早就在 `Falling` 里了。所以
「`Falling` 不能 coil」不是翻滚需要绕开的限制，它正是**把那次按键原封不动交给落地判定**
的原因。

### 🎯 这个动作是干什么用的

owner：「一般用于速通跳过更宽的沟而不触发 StepUp 减速，或者关卡强制要求缩腿避免被下面的
铁刺扎伤」。

两个用途来自这个动作的两半：

* **探测全关** → 过沟时不会被 `StepUp`（`VaultTypes` 里的一行，走 `bCheckForVaultOver`）
  抓住并减速。不需要为它写任何特殊逻辑，能力矩阵里那三个 false 就是全部。
* **脚抬起来** → 躲开下方的伤害体积。

⚠️ 代价也来自同一半：owner 「在此期间无法触发 StepUp 或 Grab，所以这个技巧有一定的风险，
判断失误可能就会直接撞到障碍边缘掉下去摔死」。**够不到边缘是这个动作本身，不是缺陷。**

### ⛔ 一条实现禁令：**不许检测身体下方有没有地面**

这条单独列出来，因为它看起来像个显而易见的好主意，而它会把整个动作废掉。

复刻时我给 coil 加了一个「每 tick 检查站立胶囊放不放得下，放不下就提前把腿放下来」的
保护，用意是防止收着腿落地后恢复胶囊把身体埋进地里。owner 一眼否掉：

> 「你不要自作主张检测胶囊下方有没有地面并提前站起来，这样违背动作的设计了，它就是用来
> 通过不蜷缩无法通过的地方，比如越过会受伤的铁丝网；另外还有个速通技巧就是使用这个技巧
> 直接精准跳进通风管道，你随手加的检测会让角色无法跳进去」

**「站立胶囊放不下」在每一个 coil 派得上用场的地方都成立。** 铁丝网上方、通风管道口、
任何只有蜷缩才过得去的缝隙——检测恰恰在这些地方最灵敏，而在这些地方把腿放下来是最坏的
结果（撞上铁丝网受伤 / 跳不进管道）。

### ✅ 落地站不起来就转蹲下

owner 给的正解，不需要任何检测：

> 「不能恢复站立，和翻滚和滑铲一样，如果当时无法站立就转蹲下；比如缩腿跳进通风管道」

原作里 `TdMove_SkillRoll` 和 `TdMove_Slide` 结束时都是这个处理，本项目的 `SkillRollMove`
与 `SlideMove` 也已经这么写了。所以 coil 落地直接交棒给 `Crouch`——蹲下自己知道什么时候
能站起来（松开蹲键 **且** 头顶有空间），没空间就一直蹲着。

📌 顺带一提：coil 期间的落地判定用的是**缩小后**的胶囊，所以收着腿会比站着晚一点触地。
那不是需要修正的误差，那就是「腿收起来了」的意思，也正是同一个抬升量把身体带过沟对岸边缘
而不是磕在上面。

## 5.3 SpringBoard（踩踏跳）

```
SpringBoardJumpZ    = 950 uu/s     ← 全游戏最大垂直冲量
SpringBoardJumpXYAdd = -100        ← 注意是负数
SpringBoardJumpXYMin = 400
SpringBoardMinHeight = 80 uu       可踩物体高度下限
SpringBoardMaxHeight = 148 uu      上限
IntermediateFootPlantHeight = 64
IntermediateFootPlantDistance = 112
CheckDistanceTime = 1.0 s
```

🔶 **推导**（用实测的 g = 1600，见 [02.4](02-速度系统.md#24-重力与跳跃)）：
950 uu/s 可跳 `950² / (2×1600)` = **282 uu = 2.82 m**，是普通跳跃（1.24 m）的 2.3 倍。

🎯 **这是对 g = 1600 的一次独立交叉验证。** ✅ owner 实测踩栏杆起跳「可以跳 2 米多」——
按旧的 g = 800 算会得到 5.64 m，与实测差了一倍多；换成实测重力后落在 2.82 m，吻合。

### ✅ 触发条件是**地形组合**，不是触发器 —— owner 实机探明

owner 在 ME 里逐个试出来的：**SpringBoard 没有触发器体积，满足条件的障碍物组合本身就是踏板。**

```
两级落差 0.6 m，水平间距 1 m，宽度无所谓
面朝方向偏离 53° 以内，按空格即触发
```

图例（两种都成立，只要存在两个高差 0.6 m、间距 1 m 的面）：

```
   ┌───────┐                        │↑1.2m
   │       │↑0.6m                   │
   │       ├────────┐               │            │↑0.6m
   │       │← 1.0m →│↑0.6m          │←   1.0m   →│
   └───────┴────────┘              ─┴────────────┴─
```

### 🎯 这解释了两个一直没解释的 CDO 参数

上面那张表里 `IntermediateFootPlantHeight` / `IntermediateFootPlantDistance`
一直只是抄下来没有释义。owner 的实测把它们对上了：


| CDO 参数                        | 值                 | owner 实测        |
| --------------------------------- | -------------------- | ------------------- |
| `IntermediateFootPlantHeight`   | 64 uu =**0.64 m**  | 两级落差**0.6 m** |
| `IntermediateFootPlantDistance` | 112 uu =**1.12 m** | 水平间距**1 m**   |

**"Intermediate foot plant"（中途踏脚）就是第二级台阶**——名字直说了它是什么：
这一跳有两次蹬踏（`StepTime1` / `StepTime2`，各 0.2 s，见下），第一次在近的那级，
第二次在远的那级。两个几何参数就是"第二只脚踩在哪"。

⚠️ 53° 这个角度在 CDO 里没有对应字段。cos(53°) ≈ 0.6，形状像一个朝向点积阈值，
但**没有确证**——记在这里是因为它是实测出来的行为，不是因为找到了它的出处。

🎯 **对移植的意义**：这不是一个需要关卡设计师放触发器的动作，是一条**探测规则**。
本项目要实现它，需要的是一个能找出"前方 1 m 内、彼此高差 0.6 m 的两个可踩面"的探针——
和 `Probes.vault_query()` 的列扫描是同一类东西，而不是一个新的触发器系统。

### ✅ 滞空特别久，是因为那几帧根本没有重力

owner 实测 SpringBoard「滞空很久」，机制根因不是冲量大，而是一个物理模式切换：

```
TdMove_SpringBoard.PawnPhysics = PHYS_Flying     ← 不是 PHYS_Falling
StepTime1 = 0.2   StepTime2 = 0.2
bCheckExitToFalling = True
```

蹬踏那两步（共 0.4 s）角色处于 **Flying**，**重力完全不作用**——所以能「踩着空气往上走」，
之后才转回自由落体。玩家感觉到的那段额外滞空，有一部分是凭空多出来的 0.4 秒。

📌 复刻时这是个可直接照搬的技巧：**用一小段无重力窗口来表达「借力」**，比调大冲量更可控——
冲量会同时改变落点，无重力窗口只改变时间。

**`JumpXYAdd = -100` 是负数**——踩踏跳会**扣掉** 100 uu/s 水平速度，同时 `XYMin = 400` 保证不低于 400。清晰的设计权衡：**用水平速度换垂直高度**。

📣 社区：速通中 springboard 常常被跳过，直接走直线更快——与"它是净损速动作"的参数解读一致。

## 5.4 Swing（横杆摆荡）

```
SwingPendulumLength         = 120 uu     摆长
ExitVelocityModifier        = 600        脱手速度系数
SwingAngleTimingOffset      = 1.0
SwingExitGravityModifier    = 0.75       脱手后重力 ×0.75
SwingExitGravityModifierTime = 0.70 s    持续 0.7 秒
```

`TdMove_SwingJump`：`GravityModifier = 0.73`、`GravityModifierTimer = 0.75`

**脱手后 0.7 秒内重力降到 73–75%**——这是一个纯粹的"手感补偿"设计：让玩家在最需要判断落点的瞬间获得额外滞空。⚠️ 这类**局部重力修改**在镜之边缘里反复出现（swing、barge、coil），是它"飘但可控"的重要来源。Godot 复刻务必保留这个手法。

## 5.5 Zipline（滑索）

```
MinZipVelocity     = 300
MinZipAcceleration = 400
ZipFadeInTime      = 0.1 s
ZipFadeOutTime     = 0.5 s
```

`TdMove_IntoZipLine`：`ZVelocityFallLimit = -600`（下落速度超过此值不能挂上）

### 5.5.1 速度没有上限，这是设计而不是 bug

✅ **屋主实测**：「滑索有可能不是直线，确实感觉像是脚本路径，而且速度似乎没有上限，
我在 ME 里滑出过 80 km/h。」

🔶 **CDO 里没有任何最大速度字段**，只有两个**下限**：

| 字段 | uu | 换算 | 含义 |
| --- | --- | --- | --- |
| `MinZipVelocity` | 300 | **3 m/s** | 最低滑行速度 |
| `MinZipAcceleration` | 400 | **4 m/s²** | 最低加速度 |

也就是说滑索不是「匀速滑行」，而是「**至少 3 m/s，并且至少以 4 m/s² 持续加速**」。
一条够长的索道积分下来就是几十 km/h——80 km/h 不是异常，是把索道做长的必然结果。

⚠️ 对我们的意义：**不要给滑索设速度上限**，也不要用固定时长的 `ScriptedMove`。
它的时长取决于索道长度和坡度，是被算出来的，不是被指定的。

### 5.5.2 其余确证字段

| 字段 | 值 | 读法 |
| --- | --- | --- |
| `HangOffset` | (0, 0, -90) | 身体吊在缆绳**下方 0.9 m** |
| `PawnPhysics` | `PHYS_Flying` | 脚本驱动，穿过本该阻挡的几何——所以「感觉像脚本路径」是对的 |
| `bDisableFaceRotation` | True | 身体不转向，保持索道方向 |
| `ZipFadeInTime / Out` | 0.1 / 0.5 s | 挂上很快，脱手较慢 |
| `SameZipLineRedoMoveTime` | 3.0 s | 同一条索道 3 秒内不能重新挂上 |
| `ZVelocityFallLimit` | -600 | 下落快于 **6 m/s** 时挂不上 |

## 5.5b Swing（单杠摇摆）

### 5.5b.1 摆锤只有 1.2 m —— 所以第一次前摆就能跳

✅ **屋主实测**：「需要玩家自己用 WS 控制摇摆幅度，节奏不好有可能荡不起来……高手玩家
可以进入单杠并在第一次向前晃时直接跳出去。」

🔶 `SwingPendulumLength = 120` uu = **1.2 m**。单摆周期 `T = 2π√(L/g)`，代入本项目
标定的 g = 16：

```
T = 2π√(1.2 / 16) = 1.72 s      半周期 0.86 s     四分之一周期 0.43 s
```

**从挂上到第一个前摆极点只有约 0.43 s。** 这就是「高手第一次前摆直接跳出去」在物理上
成立的原因——不需要先荡几个来回攒幅度，第一次就到位了。摆锤做这么短是有意的。

### 5.5b.2 noob 补偿是真的，而且有三处

✅ **屋主实测**：「跳出去时受到的力与方向好像和当时的位置和角速度有点关系，但在 ME 里
感觉是有 noob 补偿的，会尽量让玩家更轻松地往前跳出去。」

这个直觉在数据里有三处对应，一处比一处强：

| 字段 | 值 | 作用 |
| --- | --- | --- |
| `SwingAngleTimingOffset` | 1.0 | 🔶 判定「现在算不算前摆」时给角度加的偏置——放宽起跳窗口 |
| `SwingExitGravityModifier` | 0.75，持续 0.7 s | ✅ 脱手后 0.7 秒内重力只有 75%，飞得更远 |
| `TdMove_SwingJump.GravityModifier` | 0.73，持续 0.75 s | ✅ 起跳分支再来一次，几乎相同的数 |
| **`TdMove_SwingJump.TargetVolumeOffset`** | **(-120, 0, -20)** | ✅ **起跳瞄准的是一个「目标体积」**，而不是纯粹的物理抛射 |

最后一条是决定性的：**单杠起跳不是「按当时的角速度施加一个力」，而是朝关卡里摆好的
目标体积去**（相对它偏移 1.2 m 后、0.2 m 下）。这解释了为什么手感上「总是能往前跳到
该到的地方」——因为它本来就是瞄着去的。

### 5.5b.3 其余确证字段

| 字段 | 值 | 读法 |
| --- | --- | --- |
| `MaxSwingVelocity` | 4.25 | 摆动速度上限（与滑索相反，摇摆**是**有上限的） |
| `ExitVelocityModifier` | 600 | 脱手时额外给 **6 m/s** |
| `PawnPhysics` | `PHYS_Flying` | 同滑索，脚本驱动 |
| `bCheckForGrab / VaultOver / WallClimb` | True | 摇摆过程中仍然在探测下一个动作 |
| `MovementGroup` | `MG_TwoHandsBusy` | 双手占用——和 Grab 同组 |

⚠️ **对我们的意义**：摇摆**不是** `ScriptedMove`。它的位置由一个自己积分的摆角决定，
玩家用 W/S 加减能量，可在任意相位脱手——更接近 WallRun 那类「运动本身带状态」的动作。
而**脱手之后**的那一跳倒是可以是脚本的，因为它有明确的目标。

## 5.6 Balance（平衡木）

```
SpeedModifier    = 0.34      速度砍到 34%
GravityInfluence = 0.3
ControlInfluence = 1.5
SpeedInfluence   = 2.5       ← 速度越快越难平衡
CameraInfluence  = 0.3
TimeToCounter    = 0.8 s     纠正窗口
```

✅ **实测确证**（2026-08，游戏内 HUD 读数）：走独木桥的速度是 **8.81 km/h**。

```
GroundSpeed 720 × SpeedModifier 0.34 = 244.8 uu/s = 8.813 km/h
```

吻合到小数点后两位。📌 注意 `SpeedModifier` 乘的是 **`GroundSpeed` 这个常量，不是你
当前的速度**——以 25.9 km/h 冲上独木桥，速度会被直接摁到 8.8，冲得多快都一样。

`SpeedInfluence = 2.5` 是**失衡量随速度放大的系数**——跑得越快越容易掉下去。配合 `SpeedModifier = 0.34` 的强制减速，平衡木是游戏里明确的**"减速关卡"**，用来给高速段落打节拍。

`TdMove_LedgeWalk.SpeedModifier = 0.1` 更极端（10%）。

## 5.6.5 谁需要兴趣点，谁不需要 —— owner 在 me_level0 里逐个查证

me_level0 里几乎有游戏里所有物件，owner 把这几个动作的关卡数据逐个翻了一遍。
结论：**ME 是两套机制并用的，而且分界线很清楚。**

| 动作 | 关卡里长什么样 | 机制 |
| --- | --- | --- |
| 平衡木 | `S_PipeSystem_*` 多段拼接，覆盖 `balance_TdBalanceWalkVolume` | 🏷️ 兴趣点 |
| 单杠 | 模型上覆盖 `swing_TdSwingVolume` | 🏷️ 兴趣点 |
| 梯子 / 水管 | 模型上覆盖 `ladder_TdLadderVolume` | 🏷️ 兴趣点 |
| 滑索 | `S_Cable`，覆盖 `zipline_TdZiplineVolume` | 🏷️ 兴趣点 |
| 踩踏跳 | 无任何标记，见 [5.3](#53-springboard踩踏跳) | 🔍 纯几何 |

### 🎯 分界线是「几何能不能自己说清楚」

踩踏跳的条件（两级面高差 0.6 m、间距 1 m）是**自明的**——地形自己就是答案，
不需要谁来声明。而一根 0.2 m 的管子是独木桥还是栏杆、一根缆绳是滑索还是电线，
几何上完全一样，只能靠标记。

**四个全带体积，一个都不缺**（滑索的 `zipline_TdZiplineVolume` 是最后找到的，
它和平衡木的一样，一开始都被当成「没有触发器」）。所以规律可以说得更硬：

> **凡是「沿着一条线交互」的动作，一律有兴趣点；几何自明的一律没有。**

📌 提醒一句：`build_blockout.py` 里那张类名表**只说明工具认识哪些类**，
不能拿来证明关卡里用了它们。本节最初就是拿它当证据推错过一轮，
后来又因为「一时没找到」把平衡木和滑索误判成无标记——**两次都错，方向还相反**。
关卡数据才是证据，而「没找到」不等于「没有」。

### 🎯 对移植的意义：标记要带一条线，不只是一个范围

owner 的落地形状：**长条矩形（或线段），表示「手或脚可以顺着这个方向交互」**，
至于是哪种交互各自实现。

这比「一个触发范围」多出来的那条**方向**是必需的，三个动作都要用它：

- 滑索 → 挂在线**下面**，沿线**滑**
- 单杠 → 挂在线**下面**，垂直于线**摆**
- 平衡木 → 站在线**上面**，沿线**走**

平衡木尤其说明问题：它是**多段管子拼接**的，靠几何每帧现推中心线会在接缝处抖，
而标记直接给一条干净的线——这条线正好又是「只能沿着它前进后退」所需要的那根轴。

✅ 而且平衡木**必须**用标记，owner 给的是玩法理由而不是实现理由：
Balance 是个**夺走控制权**的状态（不能再转向、镜头沿梁走），
误入的代价远大于漏判。用几何探测去触发一个「进去就出不来」的模式，
等于在关卡里到处埋坑。

### 观察 ✅ 实测，模型 🔶 推导：它是一个倒立摆，不是一串随机推力

这一节被改过三轮，两次都是**照字段名去推**，两次都被实测推翻。留下经过是因为
错法比结论更值得记：CDO 只给了名字和数值，没有给公式。

✅ **实测确证的只是观察本身**：站着不动也会失衡、晃动与速度无关、入场偏移随入场
速度变大、熟练者在开头调顺后几乎不再碰纠正键。🔶 **「倒立摆／拱顶上的小球」是用来
解释这些观察的模型，是推导，不是从原作里读出来的**——CDO 只给了字段名和数值，没
给公式，模型不能比它接下来用来推导的东西（下文「CDO 的四个数于是各就各位」，已标
推导、非确证）更确证。

owner 的模型：

> 手感就像在控制一个**放在拱顶上的小球**。球本身就不可能完全稳定。进入的瞬间，
> 游戏根据当时的速度把球随机摆到左边或右边的某个位置——**速度越快摆得越偏**。
> 所以刚上梁时必须立刻把身体摆正；后面的晃动完全是这个不稳定机制自然长出来的。
> 开头调顺了，后面球会很稳地待在中间，几乎不用再按 A/D。

🎯 **这一个模型解释掉了全部观察，包括互相矛盾的那两条**：

| 观察 | 倒立摆怎么解释 |
|---|---|
| 站着不动也会失衡 | 不稳定平衡：任何非零偏移自己会指数放大，**不需要任何人推你** |
| 晃动与速度无关 | 发散过程本身确实与速度无关 |
| 可是又"速度越快越难" | 速度决定的是**入场那一下的初始偏移**，不是之后的晃动 |
| 熟练者后半程不用管 | 他在开头把偏移**和它的变化率一起**归了零，发散无从起步 |
| 全程只需微调几次 | 归零之后系统就停在顶点，直到下一次扰动 |

📌 **A/D 不再转向，改成给摆一个反向的纠正力。**「失效」只对了一半：它不能再让你
横着走下梁，但它是这个状态里唯一有意义的输入。

🔶 **CDO 的四个数于是各就各位**（推导，非确证）：

```
GravityInfluence = 0.3     失衡量→横向位移的转换率，与 CameraInfluence 并列（见下）
ControlInfluence = 1.5     A/D 的纠正权重
SpeedInfluence   = 2.5     入场偏移随速度放大的倍率
TimeToCounter    = 0.8 s   发散的特征时间：偏移每 ~0.8 s 放大一个 e 倍
```

`TimeToCounter` 读成「发散时间常数」而不是「纠正窗口」，才解释得了为什么晚一点点
就彻底来不及——指数发散没有宽限期，只有时间常数。

🔶 **`GravityInfluence` 改读**（推导，非确证）：与 `CameraInfluence` 并列，两个都是
0.3，都是「把失衡量转换成某个后果」的系数——`CameraInfluence` 转成镜头 roll，
`GravityInfluence` 转成**身体真的偏离梁中心线的横向位移**，偏出半宽即脚踩空，
坠落因此是几何结果而不是又一个阈值判定。原读法「不稳定系数——偏移把自己推得更远
的强度」与 `TimeToCounter` 的「发散特征时间」说的是同一件事：在任何自洽的二阶系统
里发散速率只有一个，两个字段同时管它就必然有一个冗余——这正是改读的原因。推导过程见
`docs/superpowers/specs/2026-08-30-balance-and-ledge-walk-design.md`
「本设计对 `GravityInfluence` 的重新裁定」一节。

⚠️ **移植要点**：实现成一个二阶系统（偏移、偏移速度、正反馈），**不要注入随机推力**。
随机只出现在**入场那一次**的初始偏移里。一旦改成"每隔几秒推一下"，熟练玩家就再也
得不到那段稳定路段，而那正是这个动作给玩家的奖励。

⚠️ **屈膝跳上梁后立刻再跳可以不进入 Balance**（owner 实测的 glitch）。
📌 **本项目不复刻它**，也不要把它的缺席当成 bug 去「修」：它是原作的漏洞，
不是设计。记在这里是为了下一个人看到差异时不用重新查一遍。

⚠️ **倾斜由镜头表现，不要用身体动画。** owner：满速前进的身体倾斜片段
（`Jog_Fwd_LeanL/R`）不适合这里。这也让平衡木的动画缺口消失了——身体只是在
以 8.81 km/h 走路，`Walk` 就够，全部平衡反馈走镜头 roll。

## 5.7 Vault（翻越）

`TdMove_SpeedVault` 定义了 **6 种翻越类型**。常见的误解是"按高度和宽度分类"——实际判定轴有 **5 个**：

1. **障碍高度** `MinHeight` / `MaxHeight`
2. **落点类型** `bVaultOnto`：`true` = 翻上去站在顶上，`false` = 翻过去继续跑。**功能上等价于障碍的厚度/宽度**（对面有没有落脚地），由 `TdPhysicsMove.bCheckForVaultOver` 的探测决定
3. **垂直速度方向** `MinSpeedZ` / `MaxSpeedZ`：你到达障碍时是在上升还是下降
4. **水平速度 / 动量** `ClampSpeedMin` / `ClampSpeedMax` / `MaxMomentum`
5. **距离时间窗口** `MaxDistanceTime`（0.2 或 0.4 s）

### 完整表


| 动画                 | 高度 (uu) | 落点     | 垂直速度                   | 水平速度                        | 手部 IK           | 连携 |
| ---------------------- | ----------- | ---------- | ---------------------------- | --------------------------------- | ------------------- | ------ |
| `autostepuprightleg` | 0–48     | onto     | **−600 ~ 0**（下降/水平） | 100–300                        | 无                | —   |
| `stepuprightleg88`   | 48–148   | onto     | 0 ~ 700（上升）            | 200–700，**`MaxMomentum=200`** | 无                | —   |
| `vaultOnto`          | 64–148   | onto     | 0 ~ 10000                  | **400**–720，**`+80`**         | **左手**          | ✅   |
| `vaultOver`          | 64–148   | **over** | 0 ~ 10000                  | **400**–720，**`+80`**         | **左手**          | ✅   |
| `VaultOverHigh`      | 145–192  | **over** | **≥50**                   | 钳到 200–400                   | 无 IK（有撑手点） | —   |
| `VaultOntoHigh`      | 145–192  | onto     | **≥50**                   | 钳到 200–400                   | **双手**          | —   |

### 三条关键读法

**① 垂直速度方向是硬门槛。**
`autostepuprightleg` 要求 `MaxSpeedZ = 0`——**只在下降或水平移动时触发**；`stepuprightleg88` 要求 `MinSpeedZ = 0` 以上——**只在上升时**。两个高档位要求 `MinSpeedZ = 50`：**必须已经起跳且仍在上升**。

所以高障碍不是"跑过去自动翻"，而是**必须先跳**。这是玩家能感知到的输入差异，也是关卡节奏的一部分。

**② 同一个障碍，速度不同播不同动作。**
48–148 uu 这段高度上有两个候选：

- `stepuprightleg88`：`MaxMomentum = 200`（**上限**，动量低于 200 才用它）
- `vaultOnto` / `vaultOver`：`ClampSpeedMin = 400`（**下限**），且 `SpeedAddition = +80`

**慢慢走过去 = 爬上去；全速冲过去 = speed vault 并加速。** 这就是这个 Move 叫 `SpeedVault` 的原因——速度本身是解锁更好动作的钥匙。而且 `bIsStringable = true` 只给这两个高速变体，**只有它们能连进 movement string**（[06.3](06-Move状态机架构.md#63-movement-string显式的动作连携系统)）。

**③ 手部 IK 是显式的视觉分级。**
`bLeftHandIK` / `bRightHandIK` 两个开关直接对应"单手撑 / 双手撑"：矮的两段纯迈腿不用手，中段单手（左），最高段双手。`HandplantOffset` 给出撑手点的位置偏移——`VaultOverHigh` 的 `(0, −40, −69)` 说明手撑在明显低于身体的位置。

### ⭐ `autostepuprightleg` 不是台阶，是**跳跃失手的救援**

这一条最初被我读成"矮台阶用的动作"，是错的。把它和其余五种并排看，六个参数里有五个是异类：


| 参数              | `autostepuprightleg`        | 其余五种                    |
| ------------------- | ----------------------------- | ----------------------------- |
| **垂直速度**      | **−600 ~ 0（只在下落时）** | 0~700 / 0~10000 / 50~10000  |
| `MaxDistanceTime` | **0.2 s**                   | 0.4 s（全部）               |
| `MinHeight`       | **0（无下限）**             | 48 / 64 / 64 / 145 / 145    |
| `LedgeOffset.Z`   | **90 uu = 0.9 m**           | 60 / 25 / 25 / 5 / 35       |
| `ClampSpeed`      | **100~300（1~3 m/s）**      | 200~700 / 400~720 / 200~400 |
| 手部 IK           | 无（动画名含`rightleg`）    | 中段单手 / 最高段双手       |

**`MaxSpeedZ = 0` 是决定性的**：六种翻越里只有它要求玩家**正在下落**，其余全部要求上升。所以它只可能在跳跃的下降段触发。

组合起来读，它的用途很清楚：**玩家跳一道宽缺口没跳够，小腿撞到对面建筑的边缘，游戏在最后 0.2 秒里蹬一脚把人送上去。** `MinHeight = 0` 说明它捞的不是"障碍"而是"你差一点没够着的那个面"；`LedgeOffset.Z = 0.9 m` 是所有类型里最大的，它不把你放在边沿而是送进台面深处；没有手部 IK、动画名写着 `rightleg`，是腿的动作不是手撑。

### 容错是收费的

`ClampSpeed` 把速度钳到 **1~3 m/s**——全游戏最低的一档。对比：甜区翻越允许 4~7.2 m/s **且奖励 +0.8**，高障碍翻越允许 2~4 m/s。

**玩家花 7 秒（[02.1](02-速度系统.md#21-速度曲线核心)）爬满的速度，被一次没跳准清空到接近起点。**

这是整份研究里最值得抄的设计之一：**容错机制有明码标价**。玩家不会因一次失误就坠楼重来（那会打断心流），但也绝不会觉得"跳不准无所谓"——代价直接记在速度上，而速度是这游戏唯一的货币。

📣 该读法由所有者的游玩记忆提出（"跳宽缺口时膝盖撞到边缘会被蹬上去"），逆向参数逐条印证。参数本身 ✅ 确证，用途解读 ⚠️ 推断但证据链完整。

### 时长与惩罚


| 动画                      | `VaultTimeUp` | `Over` | `Down` | 总计       |
| --------------------------- | --------------- | -------- | -------- | ------------ |
| `autostepuprightleg`      | 0             | 0.3    | 0.2    | **0.50 s** |
| `stepuprightleg88`        | 0             | 0.4    | 0.25   | **0.65 s** |
| `vaultOnto` / `vaultOver` | 0             | 0.35   | 0.3    | **0.65 s** |
| `VaultOverHigh`           | 0.28          | 0.3    | 0.45   | **1.03 s** |
| `VaultOntoHigh`           | 0.27          | 0.3    | 0.6    | **1.17 s** |

高档位承受**三重惩罚**：速度被钳到 200–400（净降速）、耗时约 2 倍、且 `bResetCamera = true`——**强制重置镜头朝向**，打断玩家的视线规划。

其他：`VaultClearObjectHeight = 35`、`MaxTimeToLedge = 0.4 s`、`ClampSpeedMax = 720` 恰好等于 `GroundSpeed` 上限、`LedgeOffset` 的 Z 分量（90 / 60 / 25 / 25 / 5 / 35）是落点相对边缘的高度偏移。

### ⭐ 判定发生在接触前 0.2–0.4 秒，不是接触瞬间

✅ **确证**：

```
autostepuprightleg:  MaxDistanceTime = 0.2f
其余五种:             MaxDistanceTime = 0.4f
TdMove_SpeedVault:   MaxTimeToLedge  = 0.4
```

参数名里有 `Distance`，值却是 `0.2f` / `0.4f`。本文件所有真正的距离参数都是 50 / 60 / 90 / 120 / 180 / 200 / 350 这个量级——**它是时间，不是距离**，且与同类的 `MaxTimeToLedge = 0.4` 完全一致。

⚠️ 由此推断的流程（可信度高，未经字节码验证）：

```
每帧前向探测 → time_to_ledge = 距离 / 当前水平速度
若 time_to_ledge ≤ MaxDistanceTime → 用【此刻】的速度向量查变体表 → 匹配则立即转移
```

**三个后果**：

**① 前瞻窗口是速度归一化的 → 越快越流畅。** 0.4 秒在 400 uu/s 下是 160 uu 的前瞻，在 720 uu/s 下是 **288 uu**。跑得越快，越早锁定动作，而留给动画混合的绝对时间不变。「高速通过时动作最顺」不是动画做得更好，是决策提前量更充裕。

**② 起跳时机通过「评估瞬间你在上升还是下降」起作用。** 高档 vault 要求 `MinSpeedZ ≥ 50`；起跳后垂直速度从 630 衰减，保持 ≥50 只有 **(630−50)/800 = 0.725 秒**。

- 起跳**太早** → 窗口打开时已在下降 → `MinSpeedZ` 不满足
- 接触**之后**才按 → 水平速度已被碰撞吃掉 → `ClampSpeedMin = 400` 过不了

两种情况都掉出 `VaultTypes` 表，⚠️ 回退到 `TdMove_IntoGrab` → 吊挂 → `TdMove_GrabPullUp`，即**双手吊挂爬上去**，是全流程最慢的一条路。📣 这与玩家实测症状（"本来能小跳上去的障碍，碰到后再按跳就变成双手爬"）吻合。

所谓"完美起跳时机"因此有了精确定义：**让评估瞬间落在你还在上升的那 0.725 秒窗口里。**

**③ 上升与下降的能力不同：**


| Move                     | `bCheckForGrab` | `bCheckForVaultOver` | `bCheckForWallClimb` |
| -------------------------- | ----------------- | ---------------------- | ---------------------- |
| `TdMove_Jump`（上升）    | ✓              | ✓                   | **✓**               |
| `TdMove_Falling`（下降） | ✓              | ✓                   | **✗**               |

上升阶段能发起爬墙，下降阶段不能。与 `MinSpeedZ` 是同一设计思路的两种表达。

另：`TdMove_Jump` 的 `LongJumpSlowThreshold=400` / `Normal=500` / `Fast=700`——**起跳动画本身也按水平速度分三档**。

❓ **未知**：多个变体同时匹配时的优先级规则（数组顺序？最优匹配？）需要字节码才能确定。

### 更高的障碍走另一条链

超过 192 uu 就不在 `VaultTypes` 里了，改走：

```
TdMove_WallClimb（入射角 ≤33°）→ TdMove_IntoGrab → TdMove_GrabPullUp
```

即"先垂直踩墙、再抓边、再翻上去"，见 [04.2](04-墙面动作.md#42-wallclimb垂直爬墙)。

### 另一套独立的 StepUp 系统

`TdMove_StepUp` / `TdMove_AutoStepUp` 是**独立于 `VaultTypes`** 的低速分支（`StepUpSpeedLimit = 300`、`StepUpDistanceLimit = 60`），各自有三档：

```
StepUp:      Low≥33   Medium≥68   High 112–148     Optimal: 48 / 88 / 144
AutoStepUp:  Low≥33   Medium≥68   High 8–48        Optimal: 48 / 88 / 144
```

### ✅ 实测：0.35 m 是「地形噪声」与「障碍物」的分界线

✅ **游戏内实测**（2026-08）：**≤0.35 m 的凸起，走过去会被直接抬上去**，无动画、
无停顿、如履平地；而一处 **0.4 m 高的女儿墙走不上去**，必须起跳。

```
TdPawn.MaxWallStepHeight = 35 uu = 0.35 m
```

精确命中。0.4 m 卡住的原因也能解释：`autostepuprightleg` 那一档虽然覆盖 0–0.48 m，
但它要求 `MaxSpeedZ = 0`（垂直速度必须为负，即人正在下落）——走路过去时垂直速度为零，
条件不满足。所以那 0.05 m 之差把「无感通过」变成了「必须起跳」。

📌 **这条线的设计意图很清楚**：低于 0.35 m 的一切当作不存在，高于它的一律要求一个
明确输入，**中间没有含糊地带**。复刻时若把 step-up 上限设低（比如 0.2 m），城市地形里
大量的路缘、管线、通风口凸起都会变成绊脚的东西，跑动的流畅感会被碎掉。

### 设计结论

障碍高度直接决定你被奖励还是被惩罚，存在一个明确的**甜区**：

- **64–148 uu（0.64–1.48 m）**：全速冲过去给 +80 uu/s 奖励，且可连携
- **145–192 uu（1.45–1.92 m）**：必须起跳、降速、耗时翻倍、镜头被重置

**这是可以直接抄进关卡设计规范的数字。** 把障碍做成甜区高度，玩家就能保速通过；想给节奏打个逗号，就放一个 1.5 m 以上的。

## 5.8 Barge（撞击）与其他

```
TdMove_Barge:      BargeAddOnSpeed=200  BargeMaxSpeed=500
                   BargeKickThresholdSpeed=250  BargeMinTraceDistance=90  RedoMoveTime=0.1
TdMove_AirBarge:   HeightBoostDuration=0.25  TotalHeightBoost=60
TdMove_RumpSlide:  MaxSlideSpeed=1000  SideControl=350  GravityModifier=0.5
                   InitialSpeedLoss=0.75  MinSlideFloorZ=0.9
TdMove_Climb:      ClimbDownFastVelocity=200  ClimbFastUpPipeAnimRate=2.0
TdMove_GrabJump:   GrabJumpOffZHeight=160  PushAwayMax=400 / Min=200  AllowedJumpAngle=45°
TdMove_Crouch:     SpeedModifier=0.2
TdMove_180Turn:    TurnTime=0.25  FrictionModifier=0.3
```

`TdMove_Barge` 的 `BargeAddOnSpeed = 200`（上限 500）是撞门时的**加速**——撞开门比推开门快，且给速度奖励。

`TdMove_RumpSlide`（坐姿下滑）的 `InitialSpeedLoss = 0.75` 是明确的入场惩罚。

✅ **RumpSlide 不是地形规则，是材质标记**（2026-09 从 `TDPhysicalMaterials.upk` 读出）：
`TdPhysicalMaterialProperty.bEnableUncontrolledSlide`，与软着陆的 `bEnableSoftLanding`
是同一个结构体里的兄弟字段。带此标记的物理材质有 `PM_ConcreteWetSlide`、`PM_Metal_Slide`、
`PM_Tarmac_Slide`、`PM_Wood_Slide`、`PM_Water`、`PM_Glass_BulletproofSlide`、
`PM_Metal_PropFence_Slide`。它挂在**表面材质**的 `PhysMaterial` 上（Stormdrain 的水道
`M_WaterChute_01 → PM_ConcreteWetSlide`），而不是网格的 BodySetup；同一个网格可以一面是水道、
一面是普通墙。普通的陡坡没有这个标记，人站上去只会蹭下去或落不了地。
`MinSlideFloorZ = 0.9` 的含义仍是推断（本项目读作"坡面法线 Z 到 0.9 以上就结束滑行"）。

## 5.9 Vertigo：唯一确证的动态 FOV

```
TdMove_Vertigo:  ZoomFOV = 84.0   ZoomRate = 30.0   ZoomOutTime = 1.2 s   RedoMoveTime = 3.0 s
TdPawn:          Model1pFOV = 100
```

📣 社区（PCGamingWiki）：**游戏默认 FOV 为 90°**（死亡后会被 bug 强制改成 85°）。

于是 Vertigo 效果 = 站在高处边缘时 FOV 从 90° 拉到 **84°**，速率 30，退出耗时 1.2 s，冷却 3 s。触发条件在 `TdPlayerPawn`：`VertigoEdgeProbingHeight = 1000`（10 m 落差）、`VertigoEdgeProbingDistance = 70`、`VertigoEffectThreshold = 0.9`。

❓ **重要的负面结论**：这是全部配置与 CDO 数据中**唯一一处动态 FOV**。**没有找到任何"FOV 随速度变化"的曲线参数。** `Model1pFOV = 100` 是第一人称模型的独立渲染 FOV（防止手脚模型穿帮），不是视野。

这与 📣 社区/开发者资料一致：DICE 的一手访谈说他们把 FOV「开到画面开始弯曲之前的最大值」并**固定**下来，速度感来自摄像机运动而非 FOV 缩放。详见 [09](09-Godot移植指南.md) 与 [10](10-镜之边缘-like判定标准.md)。

## 5.10 相机晃动：没有程序化 head bob

❓ **重要的负面结论**：`TdGame.u` 与 `Engine.u` 全部 **2031 个 CDO** 中，**不存在任何头部晃动的幅度/频率参数**。

✅ 证据链：

1. `TdPlayerCamera` 的 CDO 只有 **40 字节**，零覆写
2. 搜遍 `bob` / `sway` / `oscillation` / `amplitude` / `frequency`，唯一命中的 `Amplitude = 1000` / `Frequency = 0.5` 属于 `SeqAct_TdCameraShake`——关卡脚本触发的爆炸震屏，与移动无关
3. `TdPlayerPawn.CalcCamera()` 内有局部变量 **`CameraAnimLocation`** 与 **`CameraAnimRotation`**——相机位移与旋转取自**动画数据**
4. `TdAnimNodeSequence.bDeltaCameraAnimation`——动画序列携带相机动画增量
5. 📣 开发者一手：DICE **移除了早期版本的 head bobbing**，目标重述为「从你的**眼睛**看世界，而不是从你的**头**」

### 实际控制相机运动的参数

✅ **动量 → 相机动画的耦合**（`TdPawn`）：

```
CameraAnimMomentumInfluence = 0.0001     ← 唯一把「跑多快」与「镜头动多少」连起来的系数
CameraForwardMax            = 50 uu = 0.50 m    ← 前向偏移上限
CameraDownwardMax           = 40 uu = 0.40 m    ← 下向偏移上限
HeadRotationTime            = 0.1 s
RotationSafeAngle           = 2200 → 12.1°
RotationThresholdAngle      = 100  → 0.55°
```

**幅度不是常数，是动量的函数**，并被硬钳在 0.5 m / 0.4 m。

✅ **「频率」的真身是动画混合时间**（`DefaultAnimation.ini`）——晃动来自跑步动画，频率即步频：

```
IntoIdleBlendTime 0.2   IntoWalk 0.1   IntoRun 0.5   IntoSprint 0.1
StopBlendTime 0.2       IntoRunAcc 0.2  ThumbStickTapBlendTime 0.2
GoesIntoWallRunBlendTime 0.6     GoesIntoJumpBlendTime 0.1
GoesIntoInAirBlendTimeFromWallJump 0.5
StartOfJumpBlendTime 0.1  InAirBlendTime 1.0  IntoLandBlendTime 1.0  IntoLandTime 2.0
FallVelThreshold 100      FallToDeathThreshold 1800
StartOfLongJumpMomentumThreshold 380
```

### ⭐ 动画速度阈值 ≠ 移动速度阈值

✅ 两套阈值是**分开**的：


|                                       | Sneak | Walk | Run                   | RunAcc | Sprint                |
| --------------------------------------- | ------- | ------ | ----------------------- | -------- | ----------------------- |
| 移动（`TdPawn`）                      | 5     | 50   | 260 (Jog) / 400 (Run) | —     | 630                   |
| 动画（`TdAnimNodeCharacterMovement`） | 1     | 200  | 380                   | 550    | **混入 690 / 满 700** |

**冲刺动画在 690 才开始混入、700 才满，而速度上限是 720。** 全速冲刺的视觉表现被锁在整个速度区间的最后 **4%** 里。

玩家花 7 秒爬满 [02.1](02-速度系统.md#21-速度曲线核心) 那条曲线，只有最后一小截才**看起来**像全速——这是把视觉奖励压到极限位置，让"到顶"这件事获得明确的画面确认。**这是一个可以直接抄的技巧**：不要让动画随速度线性变化，把最强的表现留给最后一小段。

### `TdSkelControlSpring` 是武器摇摆，不是头晃

```
EnableVelocityDependedTranslationSpring = FALSE   ← 明确关闭
EnableAccelerationBased                 = FALSE   ← 明确关闭
EnableOnSpecificWeaponType              = TRUE    ← 只对武器生效
```

参数供参考：`TimeBetweenSpringUpdates = 0.04`（25 Hz）、`SpringYaw/Pitch/RollInterpVel = 5/10/5`、`Max*DeltaOffset = 45°`、`DefaultAngularRotationLimiter = (Pitch 7282 → 40.0°, Yaw 4551 → 25.0°, Roll 4551 → 25.0°)`、三档修正量 `RotatorLarge/Medium/Small` Yaw = 1365 / 910 / 455 → **7.5° / 5.0° / 2.5°**。

⚠️ **注意那两个 `FALSE`**：速度驱动的位移弹簧与加速度驱动模式都被明确关闭。DICE 试过程序化摇晃，然后关掉了它。
