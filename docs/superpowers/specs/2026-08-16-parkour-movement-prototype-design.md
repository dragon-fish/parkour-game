# 第一人称跑酷手感原型 — 设计文档

日期：2026-08-16
状态：已定稿

---

## 1. 目标

做一个**镜之边缘风格的第一人称跑酷手感原型**。

原型的唯一验收标准是：**跑起来爽不爽**。不是关卡设计、不是美术、不是叙事。所有决策都服务于"能否快速迭代出正确的手感"。

完整的《镜之边缘》是 AAA 规模项目（第一人称专用动画、Runner Vision 关卡引导、城市美术、追逐 AI、叙事）。本文档只覆盖其地基部分：移动系统。后续内容各自需要独立的 spec。

## 2. 非目标

明确排除，避免范围蔓延：

- 关卡设计、美术风格、叙事、敌人、战斗
- 手柄支持（仅键鼠）
- 存档系统、设置菜单、本地化
- 多人联机
- 第三人称视角

## 3. 技术环境与锁定约束

| 项 | 值 | 备注 |
| --- | --- | --- |
| 引擎 | Godot 4.7.1-stable (official) | 官方版，位于 `D:\GodotEngine\` |
| 引擎调用路径 | `.engine\Godot_v4.7.1-stable_win64.exe` | 项目内 junction，指向 `D:\GodotEngine\` |
| 语言 | **GDScript** | **锁定**：C# 在 Godot 4 中无法导出 Web |
| 渲染器 | **`gl_compatibility`** | **锁定**：见下 |
| 物理引擎 | Jolt Physics | Godot 4.4+ 默认 |
| 输入 | 键鼠 | WASD + 鼠标 + Space 跳 + Shift 冲刺 + Ctrl 滑铲 |

### 3.1 渲染器锁定的理由

项目需要 Web 版本用于分发。Godot 4.7 官方文档明确：

> Godot 4 can only target WebGL 2.0 (using the Compatibility rendering method). Forward+/Mobile are not supported on the web platform.

WebGPU 亦不支持。因此 `gl_compatibility` 不是妥协而是唯一选项。

**全程不得更改此设置。** 中途切换渲染器会导致所有光照与材质观感重做。

### 3.2 GDScript 锁定的理由

Godot 4 的 C# 项目无法导出到 Web 平台。选择 GDScript 是 Web 分发需求的硬性推论。

## 4. 架构：显式状态机

### 4.1 场景结构

```
player.tscn (CharacterBody3D)
├── CollisionShape3D          # 胶囊；滑铲时切换为矮形态
├── CameraRig (Node3D)        # 相机的所有程序化效果挂载点
│   └── Camera3D
├── BodyRoot (Node3D)         # P5 预留：骨骼模型挂载点
├── Probes (Node3D)           # 环境探测射线集合
│   ├── WallLeft / WallRight  # 蹬墙检测
│   ├── VaultLow / VaultHigh  # 翻越障碍高度判定
│   └── LedgeForward / LedgeDown  # 边缘检测
└── StateMachine (Node)
    ├── Ground
    ├── Air
    ├── Slide
    ├── WallRun
    ├── Vault
    └── LedgeHang
```

`BodyRoot` 在 P0 即预留，避免 P5 加入骨骼模型时返工。

### 4.2 状态接口

状态基类 `PlayerState` 只暴露三个方法：

```gdscript
func enter(previous: StringName) -> void
func physics_update(delta: float) -> StringName  # 返回下一状态名，或 &"" 表示保持
func exit() -> void
```

**转换由当前状态自行决定。** 这是本架构的核心价值：诸如"滑铲中能否直接蹬墙"这类问题，在 `slide_state.gd` 中有且仅有一处答案，不会散落在多个文件里。

共享数据（速度、输入缓存、`MovementConfig`、探测射线结果）挂在 `player.gd` 上，状态通过引用访问。新增动作 = 新增一个状态文件 + 在相关状态中增加一条转换。

### 4.3 为何不选其他方案

- **单函数 + 布尔标志**：前两个动作最快，但到第四个动作会产生布尔组合爆炸，其中多数组合非法却无法从代码中看出。这是新手教程的常见形态，也是最常见的陷阱。
- **能力组件系统**：最解耦，但多个能力同时试图修改速度时需要额外的仲裁与优先级机制。对 4 个动作而言属过度设计。

## 5. 状态转换表

| 从 | 到 | 条件 |
| --- | --- | --- |
| Ground | Air | 离地 / 按下跳跃 |
| Ground | Slide | 按下蹲键 **且** 水平速度 > 阈值 |
| Ground | Vault | 前方射线命中齐腰障碍 |
| Air | Ground | 着地（下落高度超阈值则触发翻滚） |
| Air | WallRun | 侧向贴墙 **且** 速度足够 **且** 非刚从同一面墙脱离 |
| Air | LedgeHang | 前上方射线命中可抓边缘 |
| Slide | Ground | 减速至阈值 / 松开蹲键 |
| Slide | Air | 滑出边缘 |
| WallRun | Air | 墙跳 / 超时 / 离墙 |
| Vault | Ground / Air | 动作结束，按落点决定 |
| LedgeHang | Ground | 攀上平台 |
| LedgeHang | Air | 主动松手 |
| Slide | WallRun | **禁止** — 必须先经由 Ground 或 Air |

最后一条的"禁止"是实质约束而非形式。跑酷手感崩坏最常见的成因是允许了不应允许的转换，导致玩家发现某个动作循环可以无限加速。

**"非刚从同一面墙脱离"**：记录上一次蹬墙的墙面法线与时间戳，在冷却时间内禁止对同一法线的墙面再次触发 WallRun，防止在单面墙上反复蹬跳刷高度。

## 6. 动量系统

这是设计的核心，不是普通的移动代码。

**水平速度不由输入直接赋值**，而是通过加速度朝目标速度趋近。关键规则：

- **空中控制系数远低于地面** —— "跳出去就得认"的来源。这是玩家必须在起跳前规划路线的机制基础。
- **滑铲给予一次性速度加成**，随后按摩擦曲线衰减；下坡滑铲衰减减弱甚至净加速。
- **蹬墙不掉速**；墙跳将一部分水平速度转换到新方向。
- **翻滚落地保留大部分水平速度**；普通落地按下落高度扣速。这是"奖励熟练度"的具体实现。

设计意图一句话概括：**速度难攒、易丢，丢了要重新攒。**

## 7. 参数系统与调参面板

### 7.1 MovementConfig

所有手感数值集中在 `MovementConfig extends Resource`（预计 25~35 个参数），按动作分组。禁止在状态脚本中出现魔法数字。

### 7.2 运行时调参面板

`F1` 唤出 `CanvasLayer` 面板，按动作分组的滑块，**拖动即时生效，无需重启**。

- 支持保存 / 读取预设到 `user://presets/*.tres`，便于"手感 A / 手感 B"来回对比
- 相机参数（FOV 区间、晃动幅度、倾斜角度）纳入同一面板 —— 相机与物理对手感的贡献不可分割

**此面板的服务对象是人类使用者，不是 agent。** 目的是让绝大多数调参工作可以脱离改代码的循环独立完成。

## 8. 相机

第一人称手感有相当大比例来自相机。此部分与物理完全解耦，独立于 `camera_rig.gd`：

- FOV 随速度插值（走路 75° → 全速 95°），是速度感的最大来源
- 步频晃动，幅度与频率随速度变化
- 蹬墙时相机 roll 倾斜
- 落地时相机下沉并回弹，幅度按落地冲击强度
- 高速风噪以音频表现，不使用后处理特效

步频相位由单一相位源驱动，P5 的手臂摆动复用同一相位，保证视觉同步。

## 9. 动作靶场

中央出生点，四个方向各设一个练习区，目标是 30 秒内可试完所有动作。

- **北 · 跳跃区**：间距与高度递增的浮空平台，地面标注最大可跳距离刻度
- **东 · 滑铲区**：矮通道 + 下坡 + 一道仅可滑铲通过的缝隙
- **南 · 蹬墙区**：两面平行墙（Z 字形接力）+ 一面长墙
- **西 · 翻越/抓边区**：齐腰箱体、略高于跳跃上限的平台边缘

全局功能：

- `R` 重置到出生点
- `Tab` 切换调试 HUD（实时速度 / 当前状态 / 世界坐标）
- `F1` 调参面板

## 10. 第一人称身体（P5）

### 10.1 方案：程序化 IK，非手工动画

工业界做法（镜之边缘、Dying Light、Titanfall）是**手工制作的第一人称专用动画** + 动作触发时将角色吸附到相对障碍物的标准位置。这不是 IK 问题而是对齐问题。

本项目不采用该方案，原因是**免费可商用的第一人称跑酷手臂动画实质上不存在**，且项目无动画制作能力。

采用**程序化 IK**：不使用任何动画文件，直接以代码驱动手臂骨骼的 IK 目标点。

- 跑步：手臂按步频正弦摆动，相位源与相机晃动共享
- 蹬墙：IK 目标 = 墙面探测射线的命中点
- 翻越：IK 目标 = 障碍物边缘检测射线的命中点
- 抓边缘：IK 目标 = 已有的边缘检测结果
- 翻滚落地：手臂前伸

**关键优势**：这些射线本就为物理判定而存在，IK 目标点是白送的。手部与几何体的贴合是数学上精确的，而非近似。跑酷动作的本质就是"把手放到某个具体的点上"，与 IK 的工作方式天然吻合。

**代价**：程序化动画自然度低于手工动画，会有机械感。原型阶段可接受，后续可逐步叠加细节（手指姿态、延迟跟随、二次动态）。

### 10.2 模型需求

一个 CC0 人形模型，渲染时仅显示手臂与腿，隐藏躯干与头部（否则第一人称会看到自身颈部内壁）。Quaternius / Kenney 有可用的 CC0 资源。

### 10.3 排期理由

P5 对 P1~P3 建立的探测射线有硬性依赖，且各动作时长需先锁定。P0~P4 期间玩的是无身体版本 —— 这在调参阶段是**特性而非缺陷**，因为手臂会遮挡视线、干扰落点判断。

### 10.4 待查证

`SkeletonIK3D` 在 Godot 4 中的状态存疑，取而代之的可能是 `SkeletonModifier3D` 体系，亦可能需要第三方插件。**实现前必须查证 Godot 4.7 的实际 IK API，不得凭印象编写。** 若内置方案不足，需在动手前提出备选方案并确认。

## 11. 测试策略

通过 `.engine\Godot_v4.7.1-stable_win64.exe --headless` 运行自动化测试。

**测试只覆盖逻辑，不覆盖数值。** 保持轻量，不追求覆盖率。

### 11.1 核心原则：断言关系，不断言数值

手感参数将被反复调整，这是原型阶段的常态而非例外。任何写死绝对数值的测试都会在每一轮调参后失效；失效次数一多，测试就会被当作噪音而习惯性忽略 —— **那比没有测试更糟**，因为它同时消耗维护成本又不再提供信心。

因此断言的对象是**参数之间的关系**，而非参数本身的取值。这类断言在任何一组手感参数下都应当成立，调参不会使其失效。

### 11.2 覆盖范围

- **状态转换合法性**：滑铲中触发蹬墙输入不得进入 WallRun；蹬墙冷却期内不得对同一面墙再次触发 WallRun
- **关系型不变量**：滑铲后的水平速度应高于滑铲前的跑步速度；翻滚落地保留的速度应高于同等高度的普通落地；空中控制的加速度应低于地面
- **健壮性**：状态机不得进入无出口状态，不得在两个状态间无限抖动

### 11.3 明确不覆盖

- 绝对数值（如"跳跃初速为 5.5 m/s"）
- 精确落点坐标
- 手感本身

自动化保证逻辑正确性；手感优劣由人类判断。这是分工边界。

## 13. Web 导出（P6）

### 13.1 已确认的事实

- 仅支持 Compatibility 渲染器（WebGL 2.0）
- **单线程导出自 Godot 4.3 起为默认**，不依赖 `SharedArrayBuffer`，因而**不需要 COOP/COEP 响应头**。纯静态托管即可运行。
- 发布目标：`r2:cloud-epb` 桶（rclone），CDN 为 `https://r2.epb.wiki`

### 13.2 必须处理的限制

- **鼠标捕获只能在输入事件回调内触发**（浏览器安全策略）。网页版必须有"点击开始"遮罩层，玩家点击后才锁定鼠标。**否则网页版不可玩。**
- 默认 Sample 音频播放模式下混响与音频特效不可用。当前音效方案不需要，若后续需要空间混响则需切换至 Stream 模式。
- 标签页切至后台时游戏暂停。对单机跑酷无影响。

### 13.3 已知风险（用户已知悉并接受）

导出管线排在最后意味着若导出或托管环节存在问题，会在代码量较大时才暴露。已提出提前至 P0 的建议，使用者选择推迟。

### 13.4 前置条件

Web 导出需先下载导出模板（约 1GB，编辑器内 `编辑器 → 管理导出模板`）。下载走 GitHub，可能需要代理。

**每阶段结束由人类实际游玩并反馈手感，再进行调整。**
