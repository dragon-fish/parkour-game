# 镜之边缘整章分段导入设计

把一整章（第一个目标：第二章「阿杰」泄洪渠，SP02）按原作的流式分片拆成多个场景导入：
编辑时一次只打开一段，进游戏时整章一起载入，从头跑到尾。

产物照旧只进 `.private`；提取器、生成器、加载器进公开仓。

## 背景与已测得的事实

整章一次性导入（`sp02_stormdrain`，6 个分片）的结果：

| 项 | 数值 |
|---|---|
| 摆放 | 13,048（序章 4,204） |
| 灯 | 1,146（`TdAreaLight` 996） |
| 生成耗时 | **57 分钟**（序章 6 秒） |
| 编辑器打开 | 崩溃 |

生成耗时随规模远超线性增长，说明生成器里有平方级以上的环节；分段能绕开它，但病根要单独修。
分段是业界通行做法：UE3（原作）是常驻关卡 + 流式子关卡、编辑器里逐个开关子关卡；
UE5 World Partition 编辑器默认只载选中区域；Unity 是多场景叠加。共同点：编辑器只载一部分，
常驻层很轻，运行时按位置流式加载。

按下文的归属规则，泄洪渠各段的规模：

| 分段 | 摆放 | 灯 | 交互标注 |
|---|---|---|---|
| All | 2,643 | 116 | 72 |
| StdP | 2,335 | 680 | 65 |
| Roof | 2,332 | 2 | 80 |
| StdE | 2,212 | 135 | 70 |
| Std | 1,838 | 167 | 49 |
| boss | 1,644 | 46 | 45 |
| 章节常驻 | 44 | 0 | 0 |

每段都不超过序章，序章在编辑器里能正常打开。

## 范围

**做：**
- 配置新增分段模式；提取器按分段归属所有摆放、灯、标注。
- 每段一个几何场景 + 一个可编辑的分段场景；一个章节场景作为常驻层。
- 分段加载器：运行时载入全部分段；编辑器里可预览其中一段。
- 找到并修掉生成器的超线性耗时。
- 泄洪渠整章按新流程导入，跑通、测帧率。

**不做：**
- 按玩家位置加载/卸载（真正的流式加载）。加载器的接口为它留好位置，本次只做“全部载入”。
- 远景代理（HLOD）、光照贴图、灯的距离淡出。
- 分段实例化的分帧切片（见「加载」一节，本次只测量）。
- 现有单场景关卡（教程、序章、StdP）的迁移。它们不开分段模式，行为不变。

## 配置

在现有关卡配置上加一个键：

```jsonc
{
  "id": "sp02_stormdrain",
  "chapter": "SP02",
  "sections": [{ "name": "All" }, { "name": "Std" }, { "name": "StdP" },
               { "name": "StdE" }, { "name": "Roof" }, { "name": "boss" }],
  "packages": ["Stormdrain_bac.me1", "Stormdrain_Ext_Lgts.me1"],
  "split_sections": true             // 可选，默认 false
}
```

`split_sections` 为 false 时，整条流水线与现在完全相同。

## 分段归属

每个包**恰好属于一个**分段，按包名判定（前缀 `Stormdrain_` 之后的部分）：

1. 连接段 `A-B_Slc*`（以 `-` 连接两个分片名）归 **A**，也就是它的出口所在的那一段。
2. 其余包按名字的第一个词归属：`StdE_Roof_Bac` 归 `StdE`，`Std_StdE_Bac` 归 `Std`。
3. 匹配不到任何分片的包（`Stormdrain_bac`、`Stormdrain_Ext_Lgts`）归**章节常驻层**。

摆放、灯、标注都跟随它所在的包。归属结果写进提取报告，按分段列出包名和计数。

现有的分片推断（`infer_section_packages`）会把连接段同时算进两边，那只影响“加载哪些包”，
与这里的归属无关；归属是在包已加载之后另算的一步，一个包只能归一处。

## 产物

| 文件 | 内容 | 重建时 |
|---|---|---|
| `<id>_<段>_geometry.scn` | 该段的几何、BSP、灯 | 每次覆盖 |
| `<id>_<段>.tscn` | 分段场景：实例化上面的几何，外加该段的交互线、铁丝网、空气墙、死亡体积 | 仅首次或 `--rebuild-interactions` |
| `<id>_chapter_geometry.scn` | 常驻层几何（远景、全章灯） | 每次覆盖 |
| `<id>.tscn` | 章节场景：继承 `base_level`，放出生点、检查点、常驻几何、分段加载器 | 仅首次或 `--rebuild-interactions` |

分段场景的根是普通 `Node3D`，不继承 `base_level`：它不能单独游玩，只用于编辑。
灯的亮度旋钮 `energy_scale` 在每个分段场景里单独覆盖，这样 StdP（680 盏灯）可以和别的段分开调。

检查点和出生点来自章节总包 `*_p.me1`，本来就是全章的，所以放在章节场景里；
检查点落在哪一段不影响它能否使用，因为运行时全部分段都已载入。

## 分段加载器

`scripts/level/section_loader.gd`，`@tool`，挂在章节场景里：

```gdscript
@export var sections: Array[PackedScene] = []
## 编辑器专用：只把这一段实例化出来预览；空字符串表示什么都不载。
@export var editor_preview: String = ""
```

- **`sections` 用 `PackedScene`，不用路径字符串。** 这样分段就是章节场景的依赖，主菜单现有的
  后台线程加载会把它们一并载入，跑步过场照常盖住加载时间。用字符串路径的话，加载器不知道它们，
  玩家会落进还没载入的世界。
- **运行时**在 `_ready()` 里把 `sections` 全部实例化为自己的子节点。
- **编辑器里**只按 `editor_preview` 实例化那一段，节点不设 owner，所以不会被保存进章节场景；
  改成别的名字或清空时，先释放旧的预览。

**待核实：** 编辑器打开章节场景时会加载 `sections` 这些资源（只是资源，不实例化，
所以没有节点，也不渲染灯）。预计不会再崩溃，但这一点要实测；如果仍然太重，就停下来讨论。

## 加载

章节场景在白幕下切换，全部分段在同一个 `_ready()` 里实例化。这会是一个很长的帧，
违反 `docs/seamless-loading.md` 的“玩家不能操作时不许有超预算的帧”——但它被白幕盖住，
与现在单场景关卡的行为一样，只是更长。本次只测量它（`[load]` 打印），
分帧切片留到做流式加载时一起做。

## 生成器的超线性耗时

先定位再修，不猜。用单独一段（StdP 或 All）做计时，分段打印：模型库、几何构建、
几何打包保存、外壳构建、外壳打包保存。已知：模型库 2.6 秒，之后卡在“几何构建”里。
几何构建里的首要嫌疑是拉伸摆放的碰撞形状复制（`_stretched()`），它的缓存键含拉伸矩阵，
实际几乎不命中，而逐三角面碰撞每次复制都要重建整套三角形；但这只是嫌疑，以计时为准。

验收：泄洪渠整章按分段生成，总耗时与摆放数大致成线性（以序章 4,204 个摆放用 6 秒为参照）。

## 验证

- `verify_level.gd` 支持章节：实例化章节场景和全部分段后，再做现有的结构检查
  （出生点和检查点向下射线命中地面、没有 `@` 节点名、各类交互数量与清单一致）。
- 帧率：用与序章相同的探针，在出生点和至少两个检查点测 1080p 帧率、draw call、显存。
- 编辑器：每个分段场景、章节场景都能在编辑器里打开（请人确认）。
- 人进游戏从头跑一段。

公开仓测试套件不依赖私仓数据。归属规则（纯函数）和加载器的“编辑器预览不被保存”
是结构性不变量，各写一个测试。

## 未核实、需在实现中确认

- 编辑器加载 `sections` 资源的开销（见上）。
- 1,146 盏实时灯全部载入后的运行时帧率。若不可接受，灯的距离淡出是下一步，不在本次范围。
- `All` 分片的含义（名字看不出它在关卡里的位置）；按规则照常归属，截图确认。
