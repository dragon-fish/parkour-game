# 设计决定记录

## 使用者已拍板的取舍（不是待审事项）

这些是所有者本人做的决定，记录在此是为了避免日后有人（包括我）看到它们与《镜之边缘》原版不一致时，误以为是疏漏而"修正"回去。

### FOV 用 90–105，不采用原版的固定 90

调研确认原版是**固定 90° 且没有速度 FOV**，DICE 的做法是把 FOV 开到"画面开始弯曲之前"的最大值然后不动它，速度感全部来自摄像机运动。

**所有者的决定：改用 90–105 的速度驱动区间。** 理由是原版那个数字玩着难受——它是 2008 年为主机视距定的，在 PC 上偏窄。

这是**有意偏离原版**。速度 FOV 是现代第一人称跑酷的通用语汇（Titanfall、Ghostrunner 都用），只是原版明确拒绝了它。

### 保留 head bob，做成可调，之后再试头骨绑定

调研记载 **DICE 在开发过程中移除了 head bob**，理由是前庭冲突致晕，并把目标重新表述为「从你的**眼睛**看世界，而不是从你的**头**」。

**所有者的决定：先保留 bob 并做成可调**（高频 + 低幅），之后再尝试把摄像机绑定到角色模型的头骨上看效果。所有者自己的预期是"大概率很晕"。

建议的试法：把 `camera_head_follow_strength` **从 0 开始往上推**，而不是先设一个中间值。DICE 当年是直接上全跟随、15 秒就否决了——从 0 爬上去至少能定位到"晕之前"的边界在哪里，而不是只得到"这样不行"这一个结论。

### 低矮障碍免费抬升：0.35 m，镜头滞后追上

**⚠️ 给正在重构移动系统的另一个 session：这是一次已获所有者批准的小改动，改动面刻意压到最小，请不要当成遗留代码清理掉。**

**背景**：所有者在导入的《镜之边缘》教程关白盒里发现，脚踝高的杂物（`S_LitterSmall_01c`、`S_Plank_01a` 这类，实际厚度 3~9 cm）会把角色卡住过不去。

**根因**：`pawn_config.gd` 里 `max_step_height = 0.35` 一直有值但没人读，原注释写着「Godot 的 move_and_slide() 自带台阶处理」——**这句话是错的**。Godot 4 的 `CharacterBody3D` 没有台阶抬升，`floor_snap_length` 只管贴地下行。注释已更正。

**所有者拍板的两点**：

1. **阈值取 0.35 m，照抄原版 `MaxStepHeight = 35` uu。** 抬升是**免费**的：不损速、不换状态、不播动画——与原版一致，那里这是引擎级行为，玩家无从感知。
2. **镜头滞后、指数追上**（`camera_config.step_smooth_speed`，默认 12，约 0.15 秒）。刻意**不复用 `land_dip`**：落地与台阶是两个独立旋钮，理由同 `land_dip_speed_ref` 与 `land_cost_speed_ref` 当初被拆开时一样。

所有者对 0.35 m 是否偏高存疑（换算过：眼睛在脚上方 1.6 m，所以 0.35 m 约为眼高的 22%，相当于两级楼梯）。结论是**先按原版值落地，用 F1 面板现场调**——`max_step_height` 本来就是 `@export`，滑条是现成的。

**改动的文件**（全是加法，无重构）：

| 文件 | 改动 |
|---|---|
| `scripts/player/player.gd` | 新增 `try_step_up(delta) -> float`，上/前/下三段 `test_move` 试探，返回抬升量 |
| `scripts/player/states/ground_state.gd` | `move_and_slide()` 前调用一次，把返回值交给 camera_rig |
| `scripts/camera/camera_rig.gd` | 新增 `_step_offset` + `add_step_offset()`，在 `update_effects()` 里指数衰减 |
| `scripts/player/config/camera_config.gd` | 新增 `step_smooth_speed` |
| `scripts/player/config/pawn_config.gd` | 仅更正注释，**值未改** |

**刻意没做的三件事**（不是遗漏）：

1. **没有测试。** 所有者要求先出最简版本试手感，测试等确认效果后再补。**这一条在合并前必须补上。**
2. **没有接入 `SlideState` / `CrouchState`。** 滑铲撞到东西应该停下，不该自己爬上去。
3. ~~0.35~0.64 m 的高度空档没处理。~~ **已解决**，见下一节——翻越下限设成 `max_step_height` 后两段无缝衔接，不存在空档。

### 翻越的高度下限：从 `MIN_HEIGHT_EPSILON` 改为 `max_step_height`

**⚠️ 这一条最可能让你困惑，请先读完再判断。** `probes.gd` 的 `MIN_HEIGHT_EPSILON` 现在只被 `ledge_query()` 使用了，`vault_query()` 不再读它——这是**有意的**，不是重构漏改。

**症状**：所有者实测报告两个现象——低矮障碍会像 Minecraft 自动跳一样触发翻越；以及慢速走过去时被十几厘米的墙沿卡住。

**根因**：`vault_query()` 的高度下限一直是 `MIN_HEIGHT_EPSILON = 0.02`，也就是**2 厘米以上、1.3 米以下的一切都是合法翻越目标**。

那个 epsilon 从设计上只是**滤地面噪声**用的（它自己的注释写着测到过 -0.0002 / -0.0005 的浮点噪声），从来不是一条设计阈值。在没有台阶抬升之前这是**正确的**——矮障碍除了翻越没有别的出路，下限设死反而会把玩家彻底挡住。**是新增的免费台阶让它第一次变成了问题**：两个区间重叠，而翻越判定排在前面，每次都赢。

**实测确认的几何**（从导入的原版教程关白盒里查的，全关 100 处）：

| 高出脚下屋面 | 墙顶宽 | 墙体总高 | 网格 |
|---|---|---|---|
| 0.194 m | 0.640 m | **57.9 m** | `S_R_05_03_F` |
| 0.212 m | 0.760 m | **42.6 m** | `S_R_05_03_F_SP00` |
| 0.148 m | 0.640 m | 6.0 m | `S_R_05_02_F` |

楼顶四周的外墙（`_F` = facade）比屋面高出十几到二十厘米。**一堵 57.9 米高的墙，有意义的只有那 0.19 米。** 速度 ≥ `vault_min_speed` 时翻上 0.64 米宽的墙头（紧邻楼外虚空），速度不够时原地卡死。

**改动**：

```gdscript
# 之前
if height <= MIN_HEIGHT_EPSILON or height > vault_max_height:
# 现在
if height <= _config.pawn.max_step_height or height > vault_max_height:
```

**为什么复用 `max_step_height` 而不新增 `vault_min_height`**：两段边界由**同一个数**定义，就不可能漂移出空档（够不上台阶又够不着翻越）或重新重叠。调一个滑条，两边同时跟着走。

**与原版一致**：所有者确认原版里低矮障碍是直接踏上去、不播翻越动画；逆向数据也支持——原版 `vaultOnto`/`vaultOver` 的 `MinHeight = 64` uu = 0.64 m，比 0.35 还高一截。

**如果判断错了，代价是什么**：0.35 m 以下的东西玩家将无法主动翻越，只能踩过去。若日后想要"矮物也能翻"的手感，那是另一套设计（需要区分主动输入与被动通过），不是把这个下限调回去就能得到的。

**怎么改回去**：把那一行换回 `MIN_HEIGHT_EPSILON` 即可，常量还在。

**如果判断错了，代价是什么**：抬升阈值偏高会让玩家觉得"我怎么飘上去了"。改一个数字即可，`try_step_up()` 整个函数也可以直接删掉，没有其他代码依赖它。

# 我在你不在场时做的决定

这份文档记录**我替你做出、但你回来后应当自己重新判断**的决定。每条都写明：我决定了什么、为什么、以及如果判断错了代价是什么。

按重要性排序，第一条最需要你亲自跑一遍再定夺。

---

## 1. 空中控制不允许减速 ⚠️ 需要你实际跑一遍再决定

**状态：已按"不允许减速"实现。**

计划里 `air_accelerate()` 的原始代码是教科书式的 Quake `AirAccelerate`。它有一个不显眼的性质：**当输入方向与当前动量相反时，它会让你减速**。

代码审查追出的具体算术：水平速度 `(0, 0, -5)`、输入方向 `(0, 0, 1)`（即按住后退键）时，`headroom = 9 - (-5) = 14 > 0`，于是照常施加加速度，结果水平速度从 `5.0` 降到 `4.8`。按 `air_accel = 12` 计算，一次 0.625 秒的跳跃里最多能放掉 **7.5 m/s**——足以把一次走速跳完全刹停。

问题在于这与计划里给这个函数写的不变量**直接矛盾**：

> only ever adds speed along the wish direction... it never brakes, so momentum carried in from another state survives — P1's slide depends on this.

**我的决定：按不变量修，禁止减速。** 保留 Quake 的投影公式（侧向空中转向仍然有效，那是有意保留的），但增加一道幅值守卫——如果这一帧的计算结果会让水平速度变小，就跳过这一帧。效果是：满速时按侧向键仍能改变方向，按后退键则完全无效。

**理由：**

1. spec 明写核心手感是"**跳出去就得认**"，能在空中把自己刹停与之矛盾。
2. P1 的滑铲要把加速带进空中，而反向输入能抹掉它。
3. 改动只有三行，随时可逆。

**如果我判断错了，代价是什么：** 你失去了"跳出去之后中途反悔"的能力，而部分玩家会预期有这个能力。

**怎么改回去：** 删掉 `air_accelerate()` 里的幅值守卫即可恢复成标准 Quake 行为。另外 `air_accel` 本身就在 F1 调参面板里，你可以先拖动它感受一下强弱，再决定要不要动函数形状。

**建议你这样验证：** 全速冲刺起跳，在空中按住 `S`。现在的行为是速度纹丝不动。如果你觉得"应该能刹一点"，那就是我判断错了。

## 2. 走下平台边缘时的向下顿挫（已修）

`GroundState` 每帧会写入一个向下的速度偏置，用来防止跑动时 `is_on_floor()` 抖动。但这个偏置会被带进 `AirState`，导致**走下平台边缘时不是干净的抛物线，而是先向下一顿**。

代码审查最初只把它作为"状态脚本里出现魔法数字"的洁癖问题（Minor）提出，但我判断它的副作用是**真实的手感缺陷**，所以提升优先级修掉了：偏置值移入 `MovementConfig.floor_snap_speed`（因此出现在 F1 调参面板里可调），并且在"走下边缘"这条转移路径上把垂直速度清零——**跳跃路径不受影响**，跳跃冲量完整保留。

**如果我判断错了，代价是什么：** 多了一个可调参数。行为上更接近预期，很难说是坏事。

---

## 3. 场景改为代码生成，不再手工搭建

计划原本要求你在 Godot 编辑器里手动新建场景、拖节点、在检查器里连引用。你不在，这条路走不通。

**我的决定：改为生成器脚本。** `tools/build_player_scene.gd` 和 `tools/build_main_scene.gd` 在代码里搭好节点树，用 `PackedScene.pack()` + `ResourceSaver.save()` 让引擎自己吐出 `.tscn`。格式由引擎保证，没有手写猜测的成分。

实测确认往返完整：节点结构、`transform`、内联子资源、`set_script()` 附加的脚本、`@export` 的资源引用以及 `@export` 的同场景节点引用，全部原样还原。

**注意事项：** 生成器是**一次性脚手架**。`.tscn` 一旦生成，它就是唯一事实来源。**如果你之后在编辑器里改了场景，再跑一次生成器会覆盖掉你的改动。** 每个生成器文件头部都写了这句话。

**如果我判断错了，代价是什么：** 场景变成代码生成产物而非手工作品。你仍然可以正常在编辑器里打开和编辑它们。

---

## 4. Task 5 与 Task 6 合并执行

计划把"Player + 地面状态"和"空中状态"拆成两个任务。实际执行时发现这个边界划错了：`Player._build_state_machine()` 同时注册两个状态，而 `StateMachine.start()` 要求它们都已存在——**状态机没有两个状态根本起不来**。

**我的决定：合并成一个任务。** 三者是一个原子单元。

**如果我判断错了，代价是什么：** 审查面变大了一些，空中控制和地面移动是一起审的，而不是分开两轮。
